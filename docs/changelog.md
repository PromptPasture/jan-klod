# Changelog

## 2026-09-13

- **Verify**: **the release publishes the registry where `config.yaml` says it is, and a test now says so** (#139). The publishing half was already built by 16d — `release.yml` generates `index.json` through `make registry-index` **by name** (not a second copy assembled in the workflow, which would be free to drift), uploads it as an artifact, and the existing `release` job copies it to `_site/index.json` with the components at `_site/ext/`. What was missing is the part #139's Acceptance calls "probed on a runner, not only read": three paths — `registry.url` in `config.yaml`, `REGISTRY_URL` in the workflow, and the two `cp` targets — had to agree, and **only a comment said so**.
- **That is the shape #130 and #131 both cost this repository**, and it matters more here because the mistake is unobservable until a tag exists: an index published at a path `ext install` does not look at, or naming component URLs that 404, is a broken registry that every existing test would pass. `the_release_publishes_the_registry_where_config_yaml_says_it_is` reads both files and holds them together; it was probed against three realistic mistakes — `REGISTRY_URL` pointed elsewhere, the index copied under another name, the `ext/` directory never assembled — and catches all three. The deploy itself still cannot be exercised locally and remains unproven until the first tag.

- **Fix**: **`ext install` staged unverified downloads in a predictable world-readable `/tmp` path, and two installs in one process fought over it** (#168). Found while running the integration suite for #162: `a_remote_install_fetches_the_pair_and_both_signatures` failed, passed on a rerun, and the reason was in shipped code rather than in the test. `install_from_url` named its staging directory `jk-ext-fetch-<pid>` and `remove_dir_all`s it at **both** ends, so two installs in one process wiped each other's half-fetched files — the failure was a `.minisig` that had been downloaded and then deleted by a neighbouring thread. Same collision shape as #165, one layer down and in production.
- **The half that outlives the flake is the path itself.** What lands there is a component, its manifest and both signatures **before any of them is verified**, read back out of that directory to be checked — and `create_dir_all` leaves it world-readable, at a name anyone can guess, in a shared `/tmp`. The repository already had the answer one directory over: `wasm_cache::ensure_private_dir` creates the compile cache `0700` for a reason `security-model.md` states as "the cache key says nothing about who else can write into the directory that key is read from". That argument is stronger here, since the compile cache at least holds artefacts this process produced. The staging directory is now per call and private, with a row in the ledger and a test naming it. `ext_install` failed intermittently before and passes 21/21 across eight consecutive runs now.

- **Fix**: **a tool call and its result now read the same over REST as over stdio** (#161, #162 — two halves of one gap, so one change). `Notification::ToolInvoked` carried `{ id, name, arguments }` and the SSE `tool` frame carried two of the three, so a client connected with `--addr` could not render the collapsed line that names *what a call did* — the edited path lives in `arguments` — while a client on a pipe could. A connection detail was deciding what the transcript could say.
- **The other half is that nothing anywhere said a tool call had failed.** `ToolOutcome` was `{ tool_call_id, content }`, `ToolInvoker::invoke` returned `Option<String>`, and both frames carried content and nothing else — so a failed call and a successful one were the same shape before the conductor even saw them. The only way a client could tell was to match the sentences the core happens to write: ``tool `X` error:``, ``tool `X` trapped``, `tool call denied:`. Renaming "trapped" to "panicked" would have drawn a failure green with no test failing anywhere, because nothing asserted the two sides agreed on the phrasing. `failed` is now a field on `ToolOutcome`, `Event::ToolResult` and both wire frames, and `blocks.rs`'s prose matcher is deleted rather than kept as a fallback.
- **A guest interceptor cannot launder a failure into a success, and that needed a guard rather than an assumption.** `wit/interceptor.wit`'s `tool-outcome` has no `failed` field and deliberately did not gain one: rewriting `content` is a `tool-result` interceptor's business — redacting a secret out of a result is why the hook exists — and whether the call failed is not. But that means a guest's `Replace` arrives back through `from_gen_state` as `failed: false` whatever the truth was, so a denial could have returned from the round trip drawn as a success. `interceptor_host::preserve_tool_result_failed` restores the host's own verdict across the boundary, with a row in `security-model.md` and two tests.
- **The test is that the two surfaces agree, not that each is right alone.** They had already drifted once, which is what #161 was. `every_turn_event_frame_fits_its_notification` only ever checked that a frame's keys reach its notification — a subset, deliberately, because `tool` carried less. With that asymmetry gone, `tool_invocation_frames_and_notifications_carry_exactly_the_same_fields` holds the stronger claim for the two invocation frames. `protocol.schema.json` regenerated. An older core sending no `failed` key parses as `false` rather than as a malformed frame: refusing it would turn a version disagreement into a broken turn, and that is what `hello` is for.
- **What the flag bought, as the test that replaced the corpus.** `every_failure_the_core_writes_is_recognised` pinned the six sentences the matcher knew, and was honest about being a convention. Its two worries are now unreachable rather than guarded, so the new test points its fixtures the opposite way to the flag — a successful call whose output quotes `tool call denied:`, and a failure phrased in words no list would have held. A prose matcher gets both wrong; reading the flag cannot.

- **Fix**: **two `@`-completion tests shared one temp directory, so the gate went red about one run in six** (#165). Found while verifying #161 — `cargo test --workspace` failed once and passed on a rerun, in a file neither issue touched. `paths::tests::tree` named its fixture directory after the process id and `SystemTime::now().as_nanos()`, which reads as unique and is not: **macOS's clock has microsecond granularity**, so `as_nanos()` always ends in three zeros and 179 of 200 consecutive readings measured identical. Rust runs the four tests as threads of one process, so two calling `tree()` together got the same name and the same directory — one test's 70 `fileNNN.txt` fixtures landing in another's tree, and whichever finished first deleting the other's root mid-walk.
- **A process-wide atomic counter replaces the clock**, so collision is impossible by construction rather than unlikely by resolution, and the fixture clears any tree a previously panicking run left behind rather than inheriting it. It failed roughly one run in six before and passes 20 consecutive runs now. Worth the entry because of *which* assertion it was breaking: a cap test that fails intermittently is the worst kind, since "the cap did not bind" and "another thread deleted my files" are indistinguishable from the output — and it made every `make gate` result in the repository probabilistic.

- **Fix**: **the first command on every entry point now works** (#126). `README.md`, `docs/quickstart.md` and `pages/index.md` all opened with an installer that 404s: `gh release list` and `git tag` are both empty, so the very first instruction a new reader met ended in `error: could not determine latest release tag` and exit 1. Nothing was broken — `scripts/install.sh` looks up the latest release, does not find one, says so clearly and fails — three pages were promising a path with nothing behind it.
- **Say what is true until then, rather than cutting a release to make the sentence honest.** All three now lead with the build-from-source route — `make bundle DIST=coding`, which produces the same archive a release publishes — and keep the installer below it, labelled as the path once there is a tag, with what it prints today. A reader who tries the first command is no longer simply stuck. Cutting `v0.1.0` is the other way this closes, and it is deliberately not taken yet: #93 says signing should land **before** the first release, not after it, and there is no unsigned release in the wild to fix.

- **Decide**: **`muted` carries no contrast floor, because no value it could take would clear one** (#135, option C). On a light terminal the status line and timestamps read at 3.05:1 on the background and 2.41:1 on the raised surface, under AA's 4.5:1 for body text; dark is fine at 5.81 / 5.39 / 4.93:1. The floor is therefore not lowered and not met — it is **replaced** by the rule the design already had: colour is information, never the only carrier of it. Anything drawn in `muted` must also be findable by position or by a `Glyph`, which is a constraint on 19g's status bar rather than on the ramp.
- **The reason it cannot simply be fixed is now a test rather than a paragraph.** `muted` is deliberately one shared step — `smoke` sits mid-ramp, equally far from either background — and the obvious response to "it fails AA on light" is to move it. Inverting the WCAG ratio against the two surfaces it must survive gives a luminance **ceiling of 0.116** from the light theme's raised surface and a **floor of 0.234** from the dark theme's code surface. They do not overlap, so no such value exists on this ramp or off it, and `no_single_ramp_step_can_give_muted_an_aa_floor_from_both_ends` says so before someone spends an afternoon finding out. If a surface ever moves far enough to make the two overlap, that test fails — which is the right moment to reopen the decision, and the only one.
- **Giving `muted` its own light-side step was checked and does not help either**: the ≤ 0.116 it would need is `ash`'s territory (0.109), which is already `secondary`. Light has only `snow` → `chalk` above the text range, so it supports two AA text tiers above a raised surface and not three. The two rejected alternatives are recorded with their costs — meeting 4.5:1 collapses `muted` into `secondary` on light, and meeting 3:1 costs the raised surface its separation from the background.

- **Fix**: **a bounded tree grep says so before the hits, not after them** (#145). `tool-fs`'s `grep` answers from at most the first 500 files of a tree and has always been honest about it — but the caveat trailed the data, and the consumer is a language model. One that greps a repository for a symbol, reads 50 hits and acts concludes the symbol appears in 50 places; the caller most likely to miss a note below the answer is the one least able to ask a follow-up.
- **The reason it is a bug and not a preference: the marker was being deleted.** `guest_fs::truncate` caps output at 64 KiB by cutting the **tail**. A trailing `[partial: …]` therefore vanished from exactly the results large enough to have hit a bound — the output read as complete precisely when it was least complete. Leading, both markers survive the cap, and a test builds a result that overflows it to prove the difference rather than assert the ordering. The ellipsis went with the move: `…[partial]` meant "and it continues past here", which is not what a header says.
- **The old assertion was reversed on purpose, not deleted to go green.** `a_bounded_walk_is_reported_alongside_the_hits` asserted `starts_with("a.rs:1:x")` — "hits come first" — and is now `a_bounded_walk_is_reported_before_the_hits`, with a comment recording what it used to say. Both new tests were probed by restoring the trailing order and watching them fail.
- **What was deliberately not done.** The cap stays: an unbounded walk over a component boundary is what it exists to prevent, and #61 already measured the guest at 1.3× native per file — below its own 3× bar — so a native `host-fs.grep` is not justified on speed. Completeness is a separate argument and is filed separately. `tool-find` renders its marker trailing too, but truncates *before* assembling its parts, so its marker is never cut; it carries the milder half of this and is out of #145's scope.

- **Chore**: **`govulncheck` no longer floats, and the pins now live where two makefiles can both read them** (#131). It was the last tool in the repository still resolving `@latest`, in the one ecosystem that had not yet paid for it — the comment recording cargo-deny's days of red CI sits a few lines above the step that invoked it. A floating *scanner* is worse than a floating formatter in a specific way: a new release can change findings, so the gate goes red on a commit that changed nothing and the fix is not obvious to whoever is holding the build. Pinned to `v1.8.0` at both call sites, `go-supply-chain` and `supervisor-supply-chain`.
- **One definition, not two, because the second one is the bug.** The two sites live in different makefiles and CI invokes `src/extensions/Makefile` **directly** (`make -C src/extensions go-supply-chain`), so it cannot inherit a variable from a parent make that never ran — and a pin copied into both is a pin that can drift, which is what #131 is about. So the version block became `versions.mk`, included by both. The `CARGO_*_VERSION`, `WASM_TOOLS_VERSION` and `WKG_VERSION` pins moved with it rather than leaving the newest entry somewhere the others are not, and the four "keep in step with … the root Makefile" comments in `ci.yml` and `ci-macos.yml` were repointed — a pin whose twin comment names the wrong file is half-unpinned.
- Verified by running both legs, not by reading the expansion: `make supervisor-supply-chain` and `make -C src/extensions go-supply-chain` each resolve `govulncheck@v1.8.0` and report no vulnerabilities.

## 2026-09-12

- **Create**: **`jan-klod --gui` opens the web client in a native window, and Phase 17's exit gate is met** (Slice 17b, #55 — #141 the cost, #142 the window, #143 packaging, #144 this record). One front-end codebase now serves the browser and the desktop: `src/web` builds the page, `src/core` serves it at `/`, and `src/gui` is a Tauri 2 shell that opens a system webview pointed at that address. No bundled browser, and no third client codebase — Vision decision 5.
- **The cost was measured before a line of the app was written, because the answer could have been "don't"** (#141). Tauri 2.11.5 **fails the unmodified root `deny.toml`** — `advisories FAILED, licenses FAILED`, eleven errors — and costs **+256 packages**, 332 CPU-seconds and 838 MB of `target/` for a 9.6 MB binary. `cargo audit` passes: none of it is a vulnerability. The full numbers, the per-crate chains and the verified minimal policy diff are recorded on #141 rather than summarised into "we looked and it was fine", which is the same as not having looked.
- **The finding that decided the shape: the MPL floor is in `wry`, not in Tauri.** Dropping Tauri for the bare webview binding was measured too — 238 packages — and it fails the *same five* MPL-2.0 licences, because `wry` depends on `dom_query` and `dirs` itself. There is no thinner Rust path to a system webview that this policy accepts unmodified, so "use something lighter" was not an available answer and the choice was genuinely take-it-or-leave-it.
- **Eleven `deny.toml` entries, named crate by crate rather than widening the gate.** The five MPL crates are `exceptions`, not `MPL-2.0` added to `allow` — so a *sixth* MPL crate appearing anywhere still fails. The six advisories are `unmaintained` with no safe upgrade, five of them one advisory-db event retiring the whole `rust-unic` project. The tempting shortcut, `unmaintained = "workspace"`, was rejected explicitly: it would also have waved through `syntect` and `tui-markdown`, silently reversing #146. Both blocks carry a scope note saying they exist for `src/gui` alone and should be deleted with it.
- **`src/gui` is its own cargo workspace, and that is the whole reason the cost is bearable.** As a member of `src/core` those 256 packages would land in its `Cargo.lock` (406 → **663**) and be resolved and built by every `cargo test`, every `cargo clippy --workspace` and every CI run — by everyone, including everyone who never opens a window. Separate, nothing on the default path reaches them: `make all` does not build it, `make gate` does not. What separation does **not** buy is a pass on the gates — `make lockfile`, `make deny` and `make audit` each name all three workspaces, so the one tree the policy was widened for is not the one that escapes it.
- **The window is a credential boundary, not a frame.** It seeds `JAN_KLOD_TOKEN` into the page's `sessionStorage` so nobody retypes a token the launcher already had — but **only when `location.origin` is the core's own**, because a Tauri initialization script runs in *every* frame the webview loads, and navigation off that origin is refused and handed to the system browser. With no token, nothing is written at all rather than an empty string the page would send as `Bearer `. `serde_json` does the escaping, since a token from the environment ends up inside a JavaScript literal. Six tests and a row in `security-model.md`.
- **The smoke test asks a real webview what it loaded.** `src/gui/tests/smoke.rs` starts the shipped binary against a forty-line `std::net` server and reads the seeded token back out of `sessionStorage` through WebKit — no HTTP dependency, in a tree already apologising for 256 packages. CI runs it under `xvfb` with `JK_REQUIRE_GUI=1`, which turns "no display, skipping" into a failure; without that flag the only suite in the repository that can legitimately skip itself would do so in silence.
- **What was actually verified in a window, and what was not** — #142 asked for these to be reported apart, so they are. **Verified** on macOS 26.6.2 (darwin/arm64), driving the bundled release binaries through a recording proxy in front of a real gateway: the window fetches `GET /` and `GET /app.js` unauthenticated (the serving allowlist), and the **real** client then issues `GET /sessions` carrying `Authorization: Bearer <token>` — so the shipped SPA booted inside the webview and used the seeded token instead of prompting. That is the whole client-bootstrap path, end to end, in the window. **Not verified:** nobody has typed a message into the window and watched a turn stream, answered an `ask` in it, or pressed cancel in it. Those need a human at a screen, which is precisely the half #142 said could not be automated. The turn path itself is unchanged and is covered by 17a through the browser (`host/tests/it/web_client.rs`), and the window loads byte-identical assets over the same REST + SSE surface — but that is an argument from equivalence, not a sighting, and the exit gate's wording deserves the distinction. **Nothing has been run on Linux at all.**
- **`#143` asked for a `gui` distribution and the repository's own page said no, so it is a second axis instead.** `scripts/distributions/README.md` already read "a distribution says what a jan-klod install is *for*. It is not a client choice — `tui` versus `gui` is how you look at the runtime" — and taking the issue literally would have copied `coding`'s guest list into a directory whose only real difference is one binary, leaving two lists to keep in step. So `DIST` still says what an install is for and `GUI=1` says whether a window ships: `make bundle DIST=coding GUI=1` produces `…-coding-gui.tar.gz`, `install.sh --gui` asks for it, and a new test fails the build if one side exists without the other.
- **The budget baseline, measured on the shipped artifact** (darwin/arm64, release, no LTO or strip). Archive **17.6 MiB** against `coding`'s 14.3 MiB — **+3.2 MiB compressed**, +10.2 MiB on disk, which is the whole of the window. Cold start to the first page request: **median 354 ms** over five runs (300–367 ms warm; **972 ms** on the genuinely first run, before the page cache). That is the number a future slice has to beat or justify; the browser path costs nothing here because the core was already serving the page.
- **One archive per platform gets a window, not three.** `headless-chat` is headless by definition and `minimal` is minimal, so only `coding` has a `-gui` variant. It rides the release job that already paid for the toolchains rather than adding a runner — the cost argument beside that matrix, and the reason the extra Tauri build is one and not three. The Linux legs gain a `webkit2gtk-4.1-dev` install; macOS needs nothing, because the webview is part of the OS.
- **A missing webview is reported, never fallen back from.** On Linux the shared library is missing before `main` runs, so `jan-klod --gui` reads the non-zero exit and names the package instead of quietly starting the TUI — a GUI that silently becomes a terminal has told the user the wrong thing about their machine. The same rule covers the shell being absent at all, which is the normal state of a developer tree: two workspaces mean two `target/` directories, and `make gui` stages the binary beside `jan-klod` so the checkout and the bundle are found by one rule rather than two.

- **Create**: **a registry index that says what a component will ask for, before you download it** (Slice 16d, #53 — #137 the format and generator, #138 reading it, #139 publishing it, #140 this record). Phase 16's exit gate is met on all four clauses. `make registry-index` writes `index.json` — name, version, `api-version`, kind, **capabilities**, description, author, url, `sha256`, signature, size per component — and `ext search` is where an operator reads that capability line. There is no interactive Configurator and the landing page is static (#63), so the command *is* the capability view rather than a stand-in for one.
- **The generator reads manifests through the host's own reader, which is the whole value of the thing.** Six of the eleven fields are the manifest's, and a shell parser would have been a second answer to what a component declares — so the index could have shown a capability line the host would not enforce. It is a `jan-klod-core` example instead, going through `ext::list`. The digest and signature describe the individual `.wasm` and its `.minisig`, never an archive, because `ext install` verifies per file; an index built on a tarball would feed nothing.
- **There was no committed artefact to diff against, so the property changed rather than the check being skipped.** `src/web/dist/` is committed and its drift check compares a rebuild with the committed bytes; `ext/*.wasm` is gitignored and a Rust wasm build is not byte-stable across machines, so a committed index would carry digests that differ per clone. What is held instead is that **two runs over one directory agree**, the second from a different working directory — and that is not sufficient on its own, since an order taken from the filesystem can agree twice by luck, so sortedness and uniqueness are asserted as properties. All three are probed on every run: a generator whose output changes, an out-of-order index and a duplicate name must each be refused.
- **An index is a directory, not an authority.** Reading one grants nothing: the entry's digest becomes the digest the existing install checks, the signature is still verified against `registry.trusted-keys`, and the manifest cross-check is the same `inspect` boot uses — so an index that lies produces a refusal rather than a component nobody vouched for. A `--sha256` the index contradicts **stops the install** instead of one winning, because two disagreeing claims about one set of bytes make neither trustworthy, and nothing is fetched.
- **`registry.url` follows `ext install`'s own rule — `http`/`https` fetches under the egress policy, anything else is a path** — which is what makes a mirrored index work with no network, and what lets the gate's "install from a static index fixture works offline" be tested without a socket. Unreadable and empty stay different answers: a 404, a malformed document, an absent file and an unknown `index-version` are each a refusal naming the file, because "the registry has nothing" would send an operator somewhere else entirely.
- **Two probes, and both found the tests honest rather than confirming them.** Dropping the index's digest made the tampered-bytes test fail as a *signature* refusal instead of a digest mismatch — which is exactly the distinction the assertion draws — and replacing the capability line with a count failed the `ext search` test. That second test runs the real gateway binary, because the rendering lives there and a library-level test would have proved the entries parse and nothing at all about the line reaching a terminal.
- **What the release leg cannot prove yet.** `release.yml` generates the index on the linux/x86_64 leg and the existing `release` job deploys it and the components beside it to GitHub Pages — no new job, since runner spend is a cost decision (#95). A workflow change cannot be run locally and no tag was pushed, so that half is unverified; Pages is also **not enabled on this repository** today, so `configure-pages` runs with `enablement: true` and the first tagged release is what creates the site. Nothing is signed either (#93, deferred until before that release), so every entry states `"signature": ""` rather than pretending, and `registry.trusted-keys` ships empty, so a first-party install still needs `--allow-unsigned --sha256`.

- **Create**: **Phase 19 opens with the vocabulary the rest of it is written in** (Slice 19a, #98 — #128 `theme.rs`, #129 this record). `src/core/ui/src/theme.rs`: one ten-step grey ramp read from either end, four accents with one meaning each, the glyph vocabulary as a type, and capability detection that takes the environment as an **argument** rather than reading `std::env` — a detector that reads a process global can only be tested by mutating one, and tests that mutate a global race each other. It ships no visible feature. Eight slices are about to draw things, and without one place that owns colour each of them picks its own `Color::Cyan`, which is what `tui.rs` did.
- **The compiler found a design gap, not a lint nit.** `ink-2` had no role among the seven the slice named, so its enum variant was dead and `-D warnings` refused the build. That is the real defect stated as a warning: a ramp step no role can reach is a shade a caller can only obtain by going around the theme, which is the one thing keeping the ramp private is for. Hence `code_surface()`, and a test asserting every step stays reachable.
- **Two tabulated values were wrong, and both were caught by a test rather than by an eye.** The contrast test computes the WCAG ratio for every (role, surface) pair in both directions of the ramp; `ash` gave secondary text **3.88:1** against the light theme's raised surface, so it moved from `#646A74`/242 to `#585D66`/240 — the value moves, the target does not. Separately, the ASCII fallback gave `+` to both *tool completed* and *diff added*, and under `NO_COLOR` the glyph is the entire signal, so two states cannot share one; tool completed is now `*`. Both were probed by restoring the original and watching the test fail.
- **The light theme carries two AA text tiers, not three, and that is arithmetic rather than preference.** `muted` is one shared step by design, and 4.5:1 against `chalk` needs a luminance of at most 0.116 while 4.5:1 against `ink-2` needs at least 0.227. No step is both, and giving `muted` its own light-side step lands it on `secondary`. It is therefore left ungated, with **#135** carrying the decision about what to do instead. #97's detection chain also lists a terminal background query "where the backend supports it" — crossterm 0.29 has no such API, so that link falls through to dark and the module says so rather than carrying a stub.

- **Create**: **the core serves the browser client at `/`, and 17a is done** (Slice 17a, #54 — #119 serving, #120 supply chain, #121 this record). The page is embedded with `include_str!`, so the binary carries it and there is no directory to ship beside it; serving it opens no API surface that was not already open. **13c was not a prerequisite after all** — the existing REST + SSE surface already pushes an `ask`, takes its answer on a second request, and turns a dropped stream into `Flow::Stop` — so #43 stays deferred, now waiting on evidence that teardown-as-cancel is the wrong shape for a browser rather than on a slice that has not started.
- **The npm leg audits the build tools, and `--omit=dev` must never be added to it** (#120). Every one of `src/web`'s packages is a devDependency — `esbuild` and `typescript`, no runtime dependencies at all — so the usual advice to audit what ships and skip the build tools would make the command scan an empty set and report "found 0 vulnerabilities" forever. `npm ci --dry-run` runs first and is load-bearing for the same class of reason: `npm audit` reads the lockfile and says nothing about a dependency that exists only in `package.json`.
- **The committed bundle had neither a test nor a drift check, and green proved nothing** (#127). `src/web/tests/turn.test.ts` passed and ran nowhere — no Makefile target and no workflow named it — while `dist/` was the first generated artifact in this repository without a regenerate-and-compare guard, so an edit that was never rebuilt would have shipped a stale page silently. Both are gates now. The drift check is possible because esbuild's output turned out to be reproducible in the strong sense: the bundle is committed from macOS and a Linux runner rebuilds it **byte for byte**, which is what makes "rebuild and diff" a check on the sources rather than on which machine ran it.

- **Create**: **`src/web` — the browser client, on two build-time dependencies and none at runtime** (Slice 17a-1, #118). The first npm tree in the repository, which makes its size a decision with consequences past this slice: #120 wires the supply-chain scan, and whatever landed here is what that scans from now on. `esbuild` over Vite (the core serves the page, so there is no dev server to justify) and no view library, so `dist/app.js` is 5.4 kB of this repository's code and nothing else.
- **Every SSE frame has an answer, and the probe caught the claim being false.** The client switches on a discriminated union mirroring `SSE_FRAME_KINDS`, and the comment first said that "no default arm" made an unhandled frame a compile error. It did not — every arm returns, so a missing case is a function that falls through, which TypeScript accepts. Adding a `thinking` frame compiled clean. A `const unhandled: never` after the switch is what actually enforces it. That guard matters here because the repository has already shipped the defect it prevents: the TUI called every `tool-result` an unknown frame while the stdio transport dropped them without a word.
- **Cancel is an `AbortController`, because there is no cancel route** — the conductor reads the dropped SSE connection as `Flow::Stop`. An `AbortError` is therefore this client cancelling rather than a failure. The SSE spellings (`delta`, `tool`, `prompt`) are deliberately left unreconciled with the protocol's notification names, as that contract's own docs instruct.

- **Feature**: **`registry-mcp` speaks MCP over a stdio child, so the inbound ecosystem port reaches the servers the ecosystem actually ships** (Slice 18c-2, #110). It spoke SSE and streamable-HTTP only, because `host-process` ran to completion — and most MCP servers distributed today are stdio processes. A `Server` now carries a `Wire`, HTTP or a child handle, and one dispatch point makes `tools/list`, `tools/call` and `reconnect` transport-agnostic rather than written twice.
- **The framing is where the care went.** Newline-delimited JSON-RPC, accumulated until a newline — a read is bounded by the host's `output-cap`, so one reply can arrive across several and treating a read as a message would truncate anything larger than an operator's number. An empty read means "nothing arrived in that window" and **not** EOF; liveness is a separate question asked of `is-running`, and conflating the two gives either a spin or an early stop.
- **A server that misbehaves is a missing capability, not a broken agent.** One that never answers is given up on after ten seconds and reported down; one that answers something that is not JSON fails on the parse. The turn runs either way, which is what the tests assert — with a wall-clock bound, because a client that hung forever would also "produce no tools" and a test satisfied by that is satisfied by the bug.
- **It needed a second interface bump, 0.2.0 → 0.3.0, for a reason the issue did not anticipate**: `mcp-registry-world` did not import `host-process` at all, so "`registry-mcp` gains `transport: stdio`" was never a guest-only change. The host half of that interface also existed only for `tool-*` guests, so the child table became a shared `host_process::Children` rather than a second copy — #109's lifetime guarantee has to hold identically for a registry instance, and a guarantee implemented twice is one that will eventually be implemented once.
- **A stdio entry names a granted child, never a command.** The operator writes the server once in `execution.long-lived` and once in `servers`, and an extension cannot introduce a program — only ask for one already named. Such a child is confined like any other command, so **by default it has no network**, which `configuration.md` now says out loud: an MCP server that calls an API will otherwise fail in a way that looks like the server being broken.

- **Feature**: **`host-process` can hold a child open, and the grant names processes rather than permitting spawning** (Slice 18c-1, #109). `exec` runs to completion, so the core could not hold a stdio MCP server, an `lsp-*` or a browser driver. `spawn`/`write-stdin`/`read-stdout`/`is-running`/`kill` do, behind `execution.long-lived: [ { name, command, args } ]` — a guest asks for a **name** and the host supplies the command, so there is no path by which a string the guest chose becomes a program. That makes it **narrower** than `execution.enabled`, not a wider version of it: `enabled: true` alone grants none, and an entry missing `name` or `command` is skipped rather than guessed. No consumer yet; `registry-mcp` using it is #110.
- **A `u32` handle rather than a `resource`, against the slice's own scope line.** That line wanted the lifetime to be "the component model's problem rather than a bookkeeping convention" — but the host must leave no orphan when an instance stops or the runtime drops, so it owns the lifetime either way, and the table it keeps to enforce that is the same table that validates a handle. What remained was: the repository's first resource, against two existing handle precedents, for the gain of not validating an integer it already tracks.
- **Confinement is reused, not restated.** `exec`'s confine-then-configure sequence became `ProcessRunner::prepared`, and both paths go through it — they differ only in what they do with the `Child`. A child that outlives its call is *more* exposed than a one-shot command, so the one place that decides how a command is bounded had to be the one place both reach it through. `read-stdout` gets a reader thread rather than a poll: the core is single-threaded and a pipe read blocks, so a child that says nothing — which a stdio server does whenever it has no reply — would otherwise hang the runtime and take the turn, the transport and every other instance with it.
- **The lifetime is proved by looking for the process.** `LiveChild`'s `Drop` kills what it holds, and the child is owned by the per-instance `ToolHost`, so it dies whether the instance stops cleanly, errors, or goes down with the runtime. The test spawns a child that reports its own pid, deliberately never kills it, and checks the pid is gone once the runtime has dropped — with `sleep` rather than `cat`, because a `cat` exits on its own when its stdin pipe closes and the test would have passed without the host killing anything.

- **The bump exposed two fixtures that had encoded the version they were testing against**, and both then passed for the wrong reason: `manifest.rs`'s version-refusal test rewrote `0.1.0` → `0.2.0` to build an "incompatible" component, which became a no-op and left it compatible; `manifests-selftest.sh` did the same in `sed` and reported that a disagreement had been *accepted* when in fact its tamper had stopped tampering. Both now derive the live version and rewrite to a distinct **major**, incompatible under both the pre-1.0 rule and the one after it.

- **Feature**: **`session/get` now carries the seq that `session/fork` takes, so a client can fork at a point it read** (#106). Fork names an event sequence number; the only command that reads a session back returned `{role, content}` with no position on it. So fork was reachable only by a caller that already knew the log's internals — which no client does. `jan-klod-ui` could not offer "fork from here" because it held the messages and not their places, and Phase 19's dialog slice excluded fork for exactly this reason.

The seqs are **sparse**: an ask, an answer, a text delta project to no message and still consume a position, so seq is a log position and not an index into the list.
- **The read shape is in the contract now, which it never was.** The protocol crate typed `Command`, `Notification` and `HelloResult`; the `session/get` *result* was untyped JSON assembled in `serve.rs`, reaching no schema and no generated client. Adding a field to it would have satisfied the issue's "the schema is regenerated" line while changing nothing in the schema — the same defect one level up, since the commands were declared ahead of any transport precisely *because the schema is what non-Rust clients generate from*. `SessionGetResult` and `TranscriptMessage` are now declared beside `HelloResult`, and the integration test parses the real served bytes into that type, so the declaration and the response cannot drift.

Probed by dropping `seq` from the payload, which fails it. Found on the way: a `session/get` queued behind a `session/message` is refused mid-turn, the same `409` REST gives, so the exchange has to be split the way the existing fork test already splits its own.

- **Fix**: **the egress policy now connects to the address it classified** (#108, `d413067`). `EgressPolicy::check` resolved a host and approved it; ureq then resolved the same name again on its way to the socket. This is the other half of #107 (`2026-09-11`), which fixed the policy being applied to the URL a caller named rather than the destination actually contacted; the two are one story about the same function, and until now only the first half was written down.

A **granted origin is trusted by name, not by address** — `network.allow` and the origins `config.yaml` names are the operator saying *this endpoint*, and re-deciding where it may point would second-guess them. `docs/concepts/security-model.md` carries that as a stated limitation rather than an omission.
- **The cost is a semver exemption, and it is commented at the call site.** `Agent::with_parts` and `Resolver` live in `ureq::unversioned`, which ureq's own docs exempt from semver. A minor bump can break the call — a compile error rather than a silent reopening, which is the right failure — so the next upgrade meets the constraint instead of discovering it. - **Feat**: **Wasmtime's own compile cache, wired into every boot — #59's measurement said Cranelift, not instantiation, is what dominates cold start at this repo's guest sizes, and this is the change it named.** #60 asked, first, whether Wasmtime's built-in cache (`Config::cache_config_load*` in the issue's own wording) meets the need before building a bespoke `.cwasm` one. It does, and by a wide margin once checked against what this workspace actually pins.
- **The built-in API had already moved by Wasmtime 46.0.3 (`Cargo.lock`; `Cargo.toml`'s `wasmtime = "46"`).** `Config::cache_config_load*` no longer exists; the current shape is `Cache::from_file`/`CacheConfig` (a struct with a `with_directory` builder) plus `Config::cache(Some(cache))` — confirmed against Context7's current `docs.rs/wasmtime` snapshot and cross-checked directly in the vendored `wasmtime-46.0.3`/`wasmtime-internal-cache-46.0.3` source, not assumed from the issue's wording or from training-data recall of an older Wasmtime. Wasmtime's own test suite proves it caches **components**, not only core modules (`components_are_cached` in `wasmtime-46.0.3/src/engine/serialization.rs`).
- **The key is Wasmtime's own, and it is more complete than a hand-rolled one could be without duplicating the compiler's internals.** `HashedEngineCompileEnv::hash` (`wasmtime-46.0.3/src/compile/code_builder.rs`) hashes the compiler's target triple, its codegen flags, its ISA flags, `Engine::tunables()`, `Engine::features()`, `Config::wmemcheck`, and `Config::module_version` — the last one specifically, per its own comment, "to catch accidental bugs of reusing across crate versions". `module_version` defaults to `ModuleVersionStrategy::WasmtimeVersion` (`wasmtime-46.0.3/src/config.rs`) and this workspace never overrides it, so a Wasmtime upgrade changes the hash. The component's own bytes are a separate term in the same hashed state (`compile_cached` in `wasmtime-46.0.3/src/compile/runtime.rs`), so a changed guest changes the key too. That is every term #60's own key proposal named (`sha256(component bytes) + wasmtime version + target triple + engine config hash`), computed by Wasmtime itself rather than re-derived here, where a missed term would silently under-key a cache of native code.
- **A corrupt or foreign artefact is already a miss, not an error, in the code this now calls.** `ModuleCacheEntryInner::get_data` (`wasmtime-internal-cache-46.0.3/src/lib.rs`) turns a read or decompression failure into `None` via `.ok()`, and the caller falls through to recompiling whenever the bytes that came back do not deserialize. #60's non-negotiable requirement was already true of the built-in cache before this change touched anything.

- **Fix**: **`make gate`'s one intermittent failure was a correct HTTP 200 being destroyed in flight, not a slow machine.** `local_model`'s fake Ollama failed one gate run in three at position 169/228 and passed in 1.7s alone. The real chain: BSD `accept()` hands back a socket that inherited the listener's `O_NONBLOCK`, so a single `read` could return part of the request or none of it; the server answered anyway and closed; **closing a socket with unread bytes in its receive buffer sends RST rather than FIN, and the RST discards the response already sitting in the client's buffer.** A complete, correct 200 — written, and partly read — destroyed by the close that followed it. - **Feature**: **an editor can drive jan-klod over ACP** — `jan-klod-gateway acp` serves the Agent Client Protocol agent side on stdio, so Zed and other ACP editors connect without a bespoke plugin: `initialize`, `session/new`, `session/prompt` with streamed `session/update`, `session/request_permission`, and `session/cancel`. No SDK and no new dependency; the framing is the one `rpc` already speaks.
- **This is the first surface where the core is a JSON-RPC *client* as well as a server, on one pipe.** ACP has the agent originate `session/request_permission` and block on the editor's answer — everything else the core serves is client→server requests plus server→client notifications. That is why this port needed the reader-thread shape `rpc` uses and the MCP port did not: while a turn runs the serving thread is inside the conductor, so something else must hold the pipe or the answer could not arrive until the turn it unblocks had already finished.
- **So an editor can do something an MCP client cannot: say yes.** A turn that wants to write stops and asks, and over ACP the question reaches the editor with the permission gate's **own** options as its `optionId`s — so nothing translates between two vocabularies and an editor cannot invent an answer the gate did not offer. Every answer that cannot be read refuses: a cancelled outcome, a selection naming no option, an empty result, a protocol error, a closed pipe. An answer this cannot understand must never *widen* a permission.
- **`stopReason` is not MCP's `isError`, and assuming it was would have lost the user's prompt.** ACP's values say why a turn *ended*: `end_turn`, `max_tokens`, `max_turn_requests`, `refusal`, `cancelled`. The spec defines `refusal` as the agent declining the whole exchange, after which "the user prompt and everything that comes after it won't be included in the next prompt" — so a *permission* refusal is `end_turn`, or blocking one tool call would tell the editor to discard what the user typed. And a turn that genuinely failed has no stop reason at all, so it is a JSON-RPC error: the opposite placement from MCP, where a failure rides in-band on a successful result. Two adapters, two conventions, neither inferable from the other.
- **A disconnected editor needs no timeout, which is better than the mechanism this was specified to reuse.** Over REST a confirmation is answered on a *second* connection, so a vanished client is invisible until a deadline expires — the reason `JK_ANSWER_TIMEOUT_SECS` exists. Over ACP the answer arrives on the same pipe: the channel closes on EOF and the parked read returns at once. Detection rather than waiting, with no deadline to tune and no window in which a single-threaded core serves nobody.

- **Fix**: **the egress policy was being applied to the URL a caller named, not to the destination actually contacted.** `http::fetch_within` checked the policy once and then let ureq follow up to ten redirects on its own, so a permitted origin answering `302 Location: http://169.254.169.254/…` reached cloud instance metadata with nothing in the way — for every guest, since that function is the single outbound path. `security-model.md` claimed "public destinations only" throughout, and the tests it cited never redirected, so nothing disagreed with it. - **The bug was demonstrated before it was fixed, and the fix was demonstrated by removing it.** A permitted origin redirecting to a loopback sentinel: without the change the call returns `200` and the sentinel's body, with it the hop is refused. Both halves matter — a test that only showed the refusal would pass equally well against a client that had simply stopped working.
- **Fixing it nearly introduced something worse.** ureq defaults to `RedirectAuthHeaders::Never` and strips `Authorization` across redirects *for you*. A hand-written loop forwarding the caller's headers verbatim would have sent a provider's API key to whatever the redirect pointed at — a credential leak created by the fix for a policy bypass. `Authorization`, `Cookie` and `Proxy-Authorization` are now dropped on every hop, matching what ureq did before, and a test carries a real-looking key through one hop to prove it does not survive the second. The general lesson is worth more than the fix: **when you replace a library's behaviour with your own loop, read what it was doing for you first** — the hole was visible in our code, the protection was not.

But prehashed signatures are Ed25519 over `BLAKE2b-512`, which `ring` cannot produce — so with `ring` alone the positive-path test could never have passed, and the standing temptation would have been to flip the flag and call it done. A test now pins the refusal.
- **Fix**: **reading a key out of `config.yaml` no longer requires the keys it has nothing to do with.** `ext install` first failed with `OPENAI_API_KEY is not set`: `Config::from_path` expands `${VAR}` in every enabled instance, which is right for booting and absurd for an install command looking up a trusted key. `Config::top_level` is the same crate and the same parse, stopping before the part that does not apply. Found by running it rather than by reading it — the error was nowhere near the code that caused it.

- **Feature**: **a command is now confined on Linux too**, so both platforms this runtime is developed and tested on refuse a stray write in the kernel rather than at a prompt. The gateway re-executes itself under an internal `confine` subcommand, applies a Landlock ruleset **to itself**, and then `exec`s the command — which becomes the same process and inherits the restriction. Reads are allowed, writes only under `execution.sandbox.writable`, and the network only if the policy says so.
- **No `unsafe` was added, and that shaped the design rather than decorating it.** The obvious way to apply Landlock to a child is between `fork` and `exec`, which means `pre_exec` — an `unsafe fn`. This workspace sets `unsafe_code = "deny"` with the note "hand-written unsafe is forbidden", and there was none anywhere in the core; the sandbox is the last place to introduce the first. `CommandExt::exec` is safe, so restricting ourselves and *becoming* the command reaches the same place with none. It also left both backends sharing one shape — replace the program with a wrapper that confines and then becomes the command — which is why the backend trait takes and returns an owned `Command`.
- **No seccomp either.** The plan for this slice proposed a seccomp filter to deny the network where Landlock could not. Landlock ABI 4 (kernel 6.7) can, and below that the runtime **refuses to run the command** rather than adding a second confinement mechanism with its own dependency and its own unsafe. A backend that cannot apply the policy it was given must fail, not approximate — and the error names both ways out (`network: true`, or `mode: approval-only`).

Reading the documentation properly produced a better design than the one it replaced — `RulesetStatus::NotEnforced` is what a kernel without Landlock returns, so requiring full enforcement detects that with no version query at all.
- **The network test tells the two failures apart, and Linux names them for you.** A connection to a closed port fails the same way a denied one does. - **Feature**: **a command run through `host-process` is now confined on macOS**, not merely confirmed. Every command is rebuilt as `sandbox-exec -p <profile> -- <command>` with a Seatbelt profile generated from `execution.sandbox`: `(deny default)`, reads allowed, writes only under the paths `writable` names, network only if the policy says so. A write outside the workspace is refused by the kernel rather than by a prompt. Linux is unchanged and still approval-only until Landlock (15c), and the boot line says which platform has no backend rather than leaving it to be inferred. `require: true` — "no command at all rather than an unconfined one" — now *permits* commands on macOS, since there is finally something to require.
- **The bug this would have shipped with, found by probing before writing: Seatbelt matches the *resolved* path.** A profile granting `(subpath "/tmp/x/work")` denies a write to `/tmp/x/work/ok`, because `/tmp` is a symlink to `/private/tmp` — and it denies it with "Operation not permitted", which is indistinguishable from the sandbox working correctly. Every temp directory a test creates lives under a symlinked path, so an uncanonicalized profile would have passed a suite asserting that escapes are denied *while also denying everything the operator granted*. The escape test would have been green and meaningless. That is why the in-workspace-write test is not a formality: it is the one case that a *missing* sandbox does not trip, and the only one that catches a *broken* profile.

The network case goes further and asserts on what a real listener *did not see*, because a connection to a closed port fails identically to a denied one.

Escaping it would mean guessing at another language's rules, and a wrong guess there does not fail loudly — it widens the sandbox. Such a path is refused instead, which costs an exotic directory name the `os` mode and costs nothing else.
- **15a's backend seam could not express the mechanism it was built for.** It handed a backend `&mut Command`, and a `Command`'s program can be read but never changed — while Seatbelt confines a command precisely by *replacing* the program. It now takes and returns an owned command, which fits a wrapper and an in-process mechanism (Landlock) alike. The only implementation 15a had was one that confines nothing, for which the two signatures are identical, so nothing could have revealed this until the second one.
- **What is not claimed.** Reads are not confined, only writes and the network — a command can still read anything the user can. A command needing a Mach service fails rather than running unconfined, which is the right direction but a rough edge. And none of it is verified by CI: these tests are macOS-only and CI runs on Linux, so a regression would land green. That gap is now its own issue rather than a footnote.

- **Decision**: **Phase 13c (WebSocket) is deferred until Phase 17 needs it**, and the obstacle is worth recording because it is not the one anyone expects. The framing is the cheap part; the *socket* is the problem. This protocol needs a read that can time out — `JK_ANSWER_TIMEOUT_SECS` exists so a client that goes **silent** rather than disconnecting cannot pin a turn open, and because the core is single-threaded that pins the whole runtime — and a read that can happen while a write does, so a mid-turn `turn/cancel` is readable between a turn's own events. `tiny_http`'s `Request::upgrade` hands back the two halves **fused**, with no `try_clone`, no `set_read_timeout` and no downcast to the socket beneath; the private accessors it builds that from are not exposed, and a mutex round the fused handle just lets the blocked reader starve the writer. That leaves a second listener or replacing the HTTP surface — both architecture decisions with a user-visible cost, and the browser client they exist for has not been started, so the choice belongs to whoever will actually open the socket. - **Feature**: **the session has one record now, and everything else is a view of it.** `entries` held a `{user, answer}` row per turn; nothing writes one any more. The transcript, the session list, resume, `GET /session/:id` and `GET /sessions` all read `core::projection::transcript`, a pure function over log rows. Phase 14's exit gate holds: a session resumed after a restart rebuilds from the log, and `POST /session/:id/fork` copies a prefix into a session that then diverges.
- **Every mapping in the projection was read off `conductor::run_turn` rather than decided.** A `follow-up` becomes a user message because that is how steering is injected; a `tool-result` becomes a `Role::Tool` message carrying the call's id because that is how the loop feeds a result back. The load-bearing one is a subtraction: **an `ask` and its answer are dropped.** The prompt is put to the *user* by an interceptor over a channel the model has no part in, so rendering the question as an assistant message would put words in the model's mouth, and the answer as a user message would make a permission click look like something the user typed. A test asserts a replayed turn cannot contain "rm -rf".
- **The strongest evidence that resume still works is that nothing had to be written to prove it.** `session_memory`'s three tests — a later turn carrying an earlier one, a session resumed across a `Runtime` restart, and replay staying bounded over 30 turns — all assert on **what the provider wire actually received**, and all passed unchanged while `replay` switched to reading a completely different table. The restart test *is* Acceptance line 1, and it already existed.

Asserted for every bound from 1 to 9 over a nine-turn log. A `follow-up` is a user message but deliberately *not* a boundary — steering continues a turn rather than starting one, and letting it consume the bound would silently shorten history.
- **Correcting one doc comment found a real cost.** `REPLAYED_TURNS` claimed it bounded "before the store read", true when it was `recent(session, 20)` in SQL. It is not now: the whole log is read and trimmed in memory, so a long session reads everything it ever logged on every turn. Correct, and a considered trade — a turn bound is not a `LIMIT` — but it grows without limit and is invisible. Filed as #85 with the SQL that would express it.
- **`GET /session/:id` serves `messages`, not `turns`.** A turn was a pair because that is what one transcript row held; the log has tool results in it, and pairing those back would either drop them or invent a shape — the two-formats-for-one-session problem reappearing at the HTTP boundary. Checked before changing it that nothing outside tests depended on the old shape: the TUI only posts messages. `AgentSession::transcript` returns `Vec<Message>` for the same reason — an entry has a namespace, a key and two timestamps, and a projected turn has none of them.
- **Retiring the transcript write made the migration compulsory rather than optional**, and that was the slice's own doing rather than a plan decision. Once `list_sessions` read the log and `transcript` projected it, a database written before the log had sessions that were **neither listed nor readable** while their rows sat there unread. So the boot converts them: each `turn-N` row becomes a `user-message` and a `done`, **dated with the row's own timestamp** — re-dating an old session to the upgrade is the one fact about it a log must not invent. Idempotent (a session with any events is skipped), and the old rows are left in place, because deleting them would make the conversion unrepeatable and irreversible in one step.

- **Implement**: **Standing permission decisions — `always` / `never`.** `interceptor-permission` asked the same question on every dangerous call, which is the failure mode that gets a security boundary switched off entirely: a gate people disable protects nothing, so ergonomics here *is* a security property. The confirmation now accepts `always` and `never` alongside `yes`/`no`, recorded per **kind of action** and consulted before asking again. The scope key is the discriminator that matters — `op` for a multi-op tool (`fs:write`), the *program* for a command runner (`shell:cargo`, from `cargo test --workspace`), the bare name otherwise — so approving writes never approves deletes, and approving `cargo` never approves `curl`. Keying on the whole argument set would never match twice; keying on the tool alone would be a blanket grant.
- **Decide**: **Standing decisions are run-scoped, never persisted, and never cover a scope escape.** Three constraints keep the convenience from eroding the boundary. (1) They live in `host-storage`, which for an interceptor is memory owned by that instance — restart the agent and it asks again, because a permission boundary must not quietly become permanently open on the strength of one click last week. (2) `Concern::EscapesScope` is **un-rememberable**: "always allow writes" is about writing files, not about writing `/etc/passwd`. This is why `Policy::review` runs the **scope check first** — if a path escape were reported second, `{"op":"write","path":"/etc/passwd"}` would surface as the rememberable `DangerousOp` and a prior "always allow `fs:write`" would wave it through. (3) Every unreadable state — a storage error, a missing entry, a stored value that is not exactly `allow`/`deny` — falls back to asking; nothing can turn a broken read into an approval, and a failed *write* still lets the current call proceed (the user is simply asked again next time) so failing to persist a convenience never fails the security decision.
- **Implement**: **`tool-git` — read-only repository inspection.** New Rust guest in [src/extensions/tool-git/](../src/extensions/tool-git/), the 16th first-party component. The fleet could read, find, grep, and edit files but was blind to version control: checking its own diff meant enabling `tool-shell`, i.e. paying arbitrary command execution for `git status`. One tool, `git`, with five ops — `status`, `diff` (`staged`?, `path`?), `log` (`count`?, `path`?), `show` (`rev`), `branch`. The guest builds the argv itself from a closed op set, so the only program it can run is `git` and the only subcommands are those five. **There is no `commit`/`checkout`/`reset`/`push` — not disabled by policy, simply not expressible in the contract**, which is the difference between a capability granted and a capability *shaped*. Caller-supplied `rev`/`path` are validated (no leading `-`, restricted charset, length cap) and a pathspec is passed after `--`, because those two values are the only argv entries the model controls and `--upload-pack=…`-style options are how a value becomes a command.
- **Decide**: **Reading a repository is not inherently side-effect-free, so every invocation is hardened.** A checkout is data the agent did not write, and git treats parts of it as *configuration*: `.git/config` can point `core.fsmonitor` at a command that runs during `git status`, `core.hooksPath` at a directory of scripts, and `.gitattributes` can name external diff/textconv drivers that run during `git diff`. "Show me the diff" on a hostile repo is therefore a code-execution path. Every call carries `--no-pager --no-optional-locks -c core.fsmonitor=false -c core.hooksPath=/dev/null -c protocol.ext.allow=never`, and the diff-shaped ops add `--no-ext-diff --no-textconv`. Aliases need no guard — git refuses to let an alias shadow a real subcommand, and only real subcommands are emitted. This is the fail-closed boundary applied one level in: the sandbox already stops the *guest* from doing anything unexpected; this stops the *repository* from doing so.
- **Fix**: **`workspace:` and `execution:` were undocumented keys the core actually reads.** `Runtime::open_workspace`/`open_process_runner` read top-level `workspace:` and `execution:` (`enabled`/`timeout-secs`/`output-cap`) from config, but neither appeared anywhere in the shipped [config.yaml](../config.yaml) — so a user who enabled `tool.shell` (as its own comment invited) got a tool that failed closed with nothing explaining why, and the deployment-wide execution switch was invisible. Both are now written out with their defaults and their default-deny semantics stated. Same class as the earlier "shipped config gave a fresh install no tools" fix: the core's real contract has to be legible in the file users edit.
- **Implement**: **`tool-fs` `grep` searches a directory tree, not just one file.** Previously `grep` took a single `path` and returned `lineno:line` — so "where is this symbol?" cost the model a `find` plus a `read` per candidate, which is the sort of turn budget a small model does not have. `grep` now defaults `path` to the workspace root and searches the whole tree when `path` names a directory (probed by whether `list-dir` succeeds — `host-fs` has no `is-dir`, and widening the contract for a two-branch dispatch is not worth it), with an optional `glob` to narrow which files are read. Tree hits are prefixed `path:lineno:line`; a single-file `grep` keeps its old `lineno:line` shape. Bounded like the walk it rides on: 400 matches, then `…[partial: stopped at the match cap]`, and a walk bound is reported separately from a match bound so the caller can tell "too many hits" from "did not finish looking". A file that cannot be read (binary, not UTF-8, gone mid-walk) is skipped — one bad file must not cost the caller the other 200 results.
- **Refactor**: **Shared `guest-fs` library for the `host-fs`-routed guests.** `truncate` was duplicated byte-for-byte in `tool-fs` and `tool-edit`, and tree-grep would have made `tool-find`'s glob matcher and bounded walk a third copy. All of it — the output cap, the glob matcher, the bounded walk, and the cost bounds (`MAX_VISITS`/`MAX_DEPTH`/`MAX_RESULTS`/`MAX_OUTPUT_BYTES`, `PRUNED_DIRS`) — now lives in [src/extensions/guest-fs/](../src/extensions/guest-fs/), a workspace member that is **a library, not a component**: it holds no WIT bindings and imports no capability, so guests stay separate sandboxed components that merely compile the same tested logic in. Cost policy now has one place to change rather than three that can drift. [src/extensions/Makefile](../src/extensions/Makefile) gained a `LIBS` list so such crates are tested but never built to wasm or staged in `ext/`.
- **Fix**: **The roadmap claimed `tool-web-search` was built; it does not exist.** No `web-search` guest is in the tree (`config.yaml` carries only a disabled config placeholder) — the Phase 8 fleet table's *(built)* marker was wrong. Corrected, and `bash/shell` marked *(built)*, which it actually is.
- **Implement**: **`tool-find` — glob discovery over the workspace tree.** New Rust guest in [src/extensions/tool-find/](../src/extensions/tool-find/), the 15th first-party component, closing the fleet's discovery gap: `tool-fs` could `read`/`grep` a path it was *given* and `tool-edit` could patch one, but nothing could **enumerate** paths — a fresh session had no way to learn what files exist short of guessing them. One tool, `find`, taking `pattern` (+ optional `path` root): `*`/`?` match within a segment, `**` spans directories, and a pattern with no `/` is expanded to `**/<pattern>` so `Cargo.toml` finds the file wherever it lives (strict glob semantics would mean "repo root only", which is never what the caller meant). The walk is **guest-side over `host-fs`'s `list-dir`** — it sees exactly what the jail exposes, so no host-side directory-walking capability had to be granted.
- **Decide**: **A glob's cost is set by the tree, not the argument — so every dimension of the walk is bounded and a bound that bites is *said*.** `**/*` in a monorepo is one token from the model and unbounded work for the runtime, the one file operation where that asymmetry exists. Four caps: 20 000 entries visited, depth 24, 500 results, 64 KiB output. Heavy build/vendor trees (`.git`, `node_modules`, `target`, `.venv`, `__pycache__`, `.jj`) are pruned unless the pattern names one literally (`target/**/*.rs` opts back in). When a cap stops the walk the result appends `…[partial: stopped at the <bound>]`, and a byte-capped list appends the count omitted — a truncated tree must never read as an exhaustive one. An unreadable subdirectory is skipped, not fatal; only a root the jail refuses is an error.
- **Fix**: **The default boot plan (`jan-klod <config> <ext>` / `make run`) could not start any tool, registry, or interceptor.** `Runtime::start_all` instantiated *every* compiled component through the neutral `extension-world` linker, which grants only `host-log`/`host-config`/`host-http` — so a `tool-*` guest (imports `host-fs`/`host-process`), `registry-*` (`host-fs`/`host-event`), or `interceptor-*` (`llm-provider`) failed at instantiation. It went unnoticed while `extensions.tool` shipped empty; enabling `tool.fs`/`tool.edit` in the previous commit made the default config fail its own boot plan with `start failed: instantiating tool.edit`. `start_all` now dispatches those categories to the **same seams `build_agent` uses** (`ToolExtension`, `SkillsExtension`/`McpExtension`, `WasmInterceptor`), with the same default-deny substrates — so the diagnostic path proves what the agent path will actually do instead of testing a linker no real guest runs under. `jan-klod serve` was never affected (it goes through `build_agent`).
- **Verify**: 14 native unit tests for the matcher and walk (segment-bounded `*`, `**` spanning zero-or-more segments, `?`, backtracking `*` on repeated prefixes, slash-less expansion, sorted recursive results, root-relative matching with workspace-relative output, prune-unless-named, unreadable-dir skip, result cap, no-match line, partial note, byte-cap truncation count); a new CM-boundary integration test [src/core/host/tests/tool_find.rs](../src/core/host/tests/tool_find.rs) drives recursive glob → pruned-dir exclusion → opt-back-in → scoped `path` → no-match → **`path: ".."` denied by the jail**, plus default-deny with no workspace. `cargo clippy -p tool-find --all-targets` clean; `tool.find` enabled in the shipped `config.yaml`; `make run` against that config now starts all 8 enabled extensions (the boot-path fix below), and `make gate` is green.
- **Implement**: **`tool-edit` — hash-anchored partial file edits.** New Rust guest in [src/extensions/tool-edit/](../src/extensions/tool-edit/), the 14th first-party component and the edit-reliability lever [small-model-harness.md](concepts/small-model-harness.md#edit-reliability-tool-edit--built) had specified but nothing implemented: until now the only way to change a file was `tool-fs`'s whole-file `write`, which is exactly the re-emit-the-whole-file failure mode small models fall into. One tool, `edit`, with three ops — `view` renders each line as `anchor|lineno|text`; `replace` swaps an anchor span (`end` defaults to `start`; empty `contents` deletes); `insert` places text `before`/`after` an anchor. `contents` must be *present* on `replace`/`insert` even when empty, so an omitted key cannot silently delete a span. An **anchor** is `fnv1a32(lineno \0 text)` in 8 hex, so it validates a line's position *and* content together: if the file changed since the model viewed it, no anchor resolves and the edit is **rejected with nothing written**. A hash collision resolves as ambiguous and is rejected the same way — a collision costs a retry, never a bad write. All I/O goes through the path-jailed `host-fs`, so the guest never touches the raw filesystem.
- **Decide**: **Recoverable edit rejections return `ok`, not `tool-error`.** `tool-callable`'s `tool-error` enum carries no message, and `tool_host` surfaces it to the model as the bare `tool \`edit\` error: ExecutionFailed` — from which a model cannot self-correct. Stale/ambiguous anchors therefore come back as an `ok` result reading `REJECTED (nothing was written): … Run op=view again and retry with fresh anchors.` `err` stays reserved for malformed arguments and `host-fs` failures. Fail-closed is about the *write*, which does not happen either way; the error channel is chosen for recoverability. This kept `wit/tool-callable.wit` unchanged.
- **Fix**: **The shipped `config.yaml` gave a fresh install no tools at all.** [docs/quickstart.md](quickstart.md) claimed "by default, only file access is enabled", but `extensions.tool` held only a disabled `web-search` placeholder — Phase 8's `tool-fs`/`tool-shell` were never added — and `interceptor.tool-selector` was disabled, so even an enabled tool is never advertised to the model at `select-tools`. Added `tool.fs` (enabled), `tool.edit` (enabled), `tool.shell` (disabled), and enabled `interceptor.tool-selector` + `interceptor.permission`. Net default posture: the agent can read and edit its workspace, every write is confirmed first, and shell execution stays opt-in — v0.1.0 completion criteria 2 and 3, which the shipped config did not actually meet.
- **Verify**: 12 native unit tests for the patch logic (anchor uniqueness across duplicate lines, span replace, delete, insert before/after, stale-anchor rejection, `end`-before-`start`, trailing-newline round-trip, output cap); a new CM-boundary integration test [src/core/host/tests/tool_edit.rs](../src/core/host/tests/tool_edit.rs) drives view → replace → **stale-anchor rejection with the file byte-identical** → re-view → insert against a real path-jailed workspace, plus default-deny with no workspace. `cargo test --workspace` in `src/core` green; `cargo clippy -p tool-edit --target wasm32-wasip2 --all-targets -D warnings` clean; `make gate` green.
