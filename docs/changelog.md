# Changelog

## 2026-09-18

- **Implement**: **Phase 20 — the surface stops being one thread, and two sessions run at once** (#169; slices #223, #225, #224, #226, #229–#231). The gate: *two clients drive turns in two sessions concurrently over REST, with an `ask` answered in one while the other streams*, proven by `gate::phase20_exit_gate_two_sessions_at_once` — whose control, in the same file, is the identical pair in **one** session, which serialises. Changing one string turns one into the other.
- **The session went behind a channel, and the seam runs the opposite way from how the plan described it** (#223). `AgentSession` is `!Send`, so it cannot be handed to a worker: the thread that built it keeps it, and the *accepting* moves off. `session_thread` is generic over what it owns and carries **no `Send` bound**, which is the property that makes it usable for the session at all — asserted by a test that owns an `Rc` and would stop compiling if a bound appeared.
- **`PromptDriver::wait_for_answer` was an accept loop, which reordered the phase** (#225). Parked on an `ask`, it called `Server::recv_timeout` itself and refused every other caller `409`. A second accepting thread would have taken the answer POST about half the time and queued it behind the very turn waiting for it. There is no ordering in which two threads accept and that design still works, so the confirmation path was dismantled **before** the transport changed. `409` now means only "nothing is pending for that session".
- **`axum` replaced `tiny_http`, net +13 packages** (#224) — 16 added, 3 removed with `tiny_http` (`ascii`, `chunked_transfer`), against an **unmodified** `deny.toml`. `tokio` was already in the lock via `wasmtime-wasi`, so the runtime was a newly *used* dependency rather than a new one. One wire-visible difference, and it is the server's choice rather than the protocol's: `hyper` writes header names lowercase. One test read the raw socket and had to stop caring about case; no other assertion moved.
- **A blocking job inside an async handler is the failure no test would have shown.** The session's queue blocks, and blocking a runtime worker for the length of a turn stalls every other request on that worker. It goes through `spawn_blocking`, and that was written into the plan before the code existed because the symptom is a surface that deadlocks under load and passes everything.
- **`GET /ws` carries the client protocol** (#226, closing #43), dispatched by the same `rpc::command` stdio uses — so the answers are the stdio answers by construction. Both things #43 said a WebSocket buys are demonstrated: an `ask` answered on the socket it came up, and a `turn/cancel` read *while the turn runs*. The queue of incoming frames is **moved into each job and handed back**, so between frames the connection loop owns it and while a turn runs the turn owns it; two consumers never exist.
- **Half of #43's blocker had dissolved before it was reached.** It gave two reasons `tiny_http`'s upgraded box could not carry a socket: no read timeout, and no way to read and write at once. The first stopped mattering in #225 — a parked `ask` reads nothing now. The second stood, and is what `axum` answered. Framing cost **8 packages**, against its estimate of ~10, including a second major of `rand` that a by-name measurement had hidden.
- **The gate was unreachable by every filed slice, and nothing said so** (#228). A turn holds the session for its whole life, including while parked, so two sessions could not stream whatever the transport was. Measured rather than argued: a second `AgentSession` costs **1.35 MB and 3.5 ms**, the store is already shared, and `Runtime` is already `Send + Sync` — so an agent per session beat making the conductor resumable, which would have touched the one component the architecture calls "mechanism only".
- **A session owns a thread, a thread owns an agent** (#229), built on first use. Concurrency is asserted on **overlap** rather than ordering — a fast turn started 300 ms into a slow one finishes first — with the same pair against a single agent as its control, because otherwise the test passes on any machine quick enough to make ordering look like overlap.
- **Nothing had ever adopted an installed extension outside a test** (#231). `grep adopt_installed src/host/src/` was empty: `ext-install`'s "callable from the next turn" was true in `install_then_call.rs` and in no surface a user can reach. It is driven now from the session loop — one place every transport passes through — and reaches **every** session at its next turn, the installer included.
- **Three defects found by tests hanging or failing, not by review.** Dropping the agent registry joined threads that an outstanding handle kept alive, so shutdown hung — `session_thread` gained a stop *message*. Retiring every agent on adoption answered `503` to sessions that had asked for nothing, so adoption bumps a **generation** instead and nothing live is stopped. And a job's answer reached its caller *before* the between-jobs hook ran, so a client's next request could race the adoption — a job now returns how to deliver, and the loop delivers after the hook.
- **Still open:** #232 (per-session state changes what `always allow` means), and 20f (`AgentSession: Send`) which none of this needed.

- **Implement**: **Phase 25 closes — an agent compiles, installs and calls its own tool inside one session** (Slice 25d, #221). Every link had a test and the chain had none: `self_extend.rs` compiled and stopped, `install_then_call.rs` began from a component someone else had built. `host/tests/it/self_extend_chain.rs` runs the join — compile offline in the jail, copy the artefact, write the manifest, hash it, install it unsigned with that digest, adopt it between turns, call it — in the shipped `self-extend` posture, with no gateway restart and no operator command.
- **The digest the installer receives is parsed out of the shell tool's own output**, not computed by the test. "Can the agent obtain a sha256" was the step #221 was filed on, and computing it in the harness would have left exactly that step unexercised. `sh -c "sha256sum … || shasum -a 256 …"` answers it.
- **The manifest is the obstacle nobody predicted.** `ext::install` refuses a component with nothing beside it — *"a component nobody can inspect is not installable"* — and cross-checks the declared capabilities against the artefact's real imports. So a self-extending agent must author a claim about its own binary that the host then verifies. Harder than the digest, and it was not in the slice's list of doubts.
- **`self-extend` never enabled the install tool.** `registry.install-tool` gates `ext-install` and `ext-search` into the fleet, was unset in the one distribution Phase 25 is about, and was documented nowhere. A booted `self-extend` advertised five tools and no installer. Found by reading the *booted fleet* while measuring #219, not by reading the YAML — which is also how the test asserts it now.
- **Vendoring is not what a jailed offline build needs.** #192 measured 34 MB and 47 crates. Measured here: the Seatbelt profile is `(deny default)` plus `(allow file-read*)` and `CARGO_HOME` is already in `BASE_ENV`, so the shared cargo cache is reachable from inside the jail with no grant — a lock file plus ~1 MB of `.crate` files does it, thirty times cheaper on a machine where disk is the constraint. Vendoring remains right for a genuinely air-gapped operator. The build's own target directory is the bigger number and is transient: 385 MB, or 168 MB with `debug = false`.
- **A component whose stem names no category is adopted into nothing, and every signal says it worked** (#222, left open). `adopt_installed` reads `<category>-<kind>` from the file stem and does not check the category against the ones it dispatches: `self-built` became category `self`, the install said "callable from the next turn", adoption returned `Ok`, and the next turn said `no tool named self-built`. The name is the agent's own choice, which is what makes this the self-extension path's problem rather than a curiosity.

## 2026-09-13

- **Refactor**: **`src/` is the Rust host workspace, and `src/core` is the `jan-klod-core` crate.** Five commits: `src/core/ui` → `src/tui`, then `config`, `host` and `protocol` out to siblings, then the root itself to `src/` so `core/core` could become `core`. Members are now direct children of their workspace root. The last step was cheap because `src/core/Cargo.toml` was **virtual** — `[workspace]`, no `[package]` — so there was no crate to relocate; a real one would have had to become its own package rather than stay a shared directory.
- **The four `workspace = "../core"` pointers are gone.** A member outside the workspace root needs one; cargo's upward search otherwise fails `edition.workspace = true` with an uninformative error. They were the price of moving members one at a time; moving the root last refunded them. `src/gui` and `src/extensions` are named in `exclude` instead: their own `[workspace]` tables already stop cargo's search, so nothing changes today, but a glob in `members` would be unsafe without it.
- **Three stale-path defects the first four moves left behind, none caught by commit.** `gate-commit` runs the *unit* suite; all three lived in the integration suite or in targets not rerun since. The pattern this repository keeps paying for — checks reading green without running — now in three shapes at once, the argument for `make gate` being the gate rather than the hook.
- **`docs/concepts/security-model.md` still cited `ui/src/*.rs`**, and `docs_match_config::the_security_model_cites_tests_that_exist` asserts every one resolves to a real file. It had been *failing* since the tui move, but was never run — the one of three that worked as designed.
- **`egress_boundary`'s "no caller hands a guest the unbounded client" loop scanned nothing and reported green.** It named `host/src/main.rs` and `ui/src/main.rs` by hand, resolved them under `src/core`, and `continue`d on files it could not read. After the moves it read zero files and passed. A security assertion that cannot find its subject must fail: it reads with `expect` now, making missing files a broken test rather than an absent binary.
- **`make sbom` was describing one crate of five.** `$(CORE)/**/*.cdx.json` was never recursive — `sh` has no `globstar` — and when members left `src/core/` four silently dropped from the merged document. Every crate is now a direct child of `src/`, so one `src/*/*.cdx.json` reaches all six. The target now counts them and refuses to merge if not six, because the previous glob silently produced a smaller SBOM instead of an error.
- **Verified from a clean target, after a stale one produced a false pass.** Carrying `src/core/target/` let cargo reuse `jan-klod-protocol`'s test binary with the *previous* `CARGO_MANIFEST_DIR` compiled in; it failed on a schema under a now-absent path while 770 tests were green on that cache. A move changing a manifest's directory is not reliably a rebuild. `cargo clean` reclaimed **68.2GiB** and the rebuild ran `make gate` at 771 passed / 0 failed / 2 skipped, plus clippy, `fmt --check`, `lockfile`, `deny`, `audit`, `sbom` and both drift checks.
- **Dated entries keep the paths written then.** `src/core/ui/tests/phase19_gate.rs` below was true on the day recorded; a log rewriting itself is not a log.

- **Create**: **three dialogs, one primitive: session switcher, help overlay, quit confirm** (Slice 19h, #105). `session/list` and `session/get` existed since 13b unused; the session id was fixed at startup with no way to see, switch, or restore sessions without restarting.
- **`tui::render_modal` is the one dialog frame** — centred, `raised()` surface, `focus()` border — and 19f's ask dialog was rebuilt onto it. `tui::every_dialog_shares_one_frame_implementation` greps for exactly one `fn render_modal` and at least four call sites, the same invariant-by-grep 19a uses for stray `Color` literals.
- **The session id stopped being a `&str` held for the event loop's lifetime.** `App::session`/`App::set_session` own it now; `App::load_session` rebuilds the transcript from `session/get` in the same call — a switch is a reload, never a stash.
- **`Transport` gained `session_list`, `session_get` and `is_stdio`.** `Rest` answers with `GET /sessions`/`GET /session/:id`; `Stdio` reads its own answer off the same pipe `create_session` used, valid only with no turn streaming. `is_stdio` lets the quit confirm say, per transport, whether a running turn survives this client exiting.
- **The sidebar (19g) is reachable as a dialog** at widths where its layout has no permanent pane — `Ctrl+B`, gated on `pane.sidebar_hidden` not a copy of `layout::regions`' width table. Pointless where the pane already exists.
- **The session switcher** (`Ctrl+S`/`/sessions`) never caches — every open issues a fresh `session/list`. Rows show id and preview, filtering both case-insensitively, marked in text not only colour.
- **The help overlay** (`?` or `/help`) renders from `keymap::BINDINGS`, grouped by `Context` — a binding without a help entry is impossible. Scrolls past modal height with `↑`/`↓`/`PageUp`/`PageDown`.
- **The quit confirm** (`Ctrl+D`, `Ctrl+C` on empty composer, or `/quit`) skips on empty sessions. Otherwise it names the session id as resumable, opens with cancel selected, and mid-turn requires a second confirmation; wording differs between stdio (genuinely lost, gateway is child) and `--addr` (not lost).
- **`role` maps `user`→`Who::You`, `assistant`→`Who::Klod`, `tool`→`ToolBlock` keyed on `tool-call-id`, `system`→dropped.** The wire carries no tool name or failure flag for replayed calls, only live notifications do, so call id stands in for the name and results are assumed successful without failure indication.
- **`/new`, `/sessions` and `/help` moved from `Pending` to `Ready`**, the rule that renamed it in 19e.
- **Out of scope:** session delete/rename (no protocol command) and fork (clients rebuilding from `session/get` have no UI concept of a log position).

- **Create**: **the frame: header, sidebar, status bar, toasts, and the responsive rules that hide and collapse them** (Slice 19g, #104). The window was a bordered transcript and input; only a startup banner said anything about the connection. This slice adds the frame around the panes 19b–19f built.
- **One keymap table, in a new `keymap.rs`, modelled on `commands.rs`.** `keymap::BINDINGS` is a `const` array of `Binding { keys, action, context }`; `keymap::hint`/`hint_narrow` render from table arguments not constants, so tests can verify the string moves when the table changes. `tui::status_hint` appends a pending prompt's `default` after the table-driven string. 19h's help overlay reads the same constant.
- **Layout is a pure function, in a new `layout.rs`.** `layout::regions(width, height) -> Frame` implements #97's responsive table: `≥100` draws sidebar, `80–99` hides it, `60–79` collapses header and trims hints, `<60` drops to single column. Height below 20 rows drops sidebar then header; below the floor, `too_small` says so. Tested at 120×32, 90×30, 70×24, 50×18 and 60×8 with no overlap or out-of-bounds regions.
- **The sidebar, in a new `sidebar.rs`, is a projection and issues nothing.** `sidebar::view(&App, SessionInfo, width, theme)` returns SESSION (id, transport, connection state, working directory truncated from left), THIS TURN (tool blocks since last `You` message, in call order, cleared by next one) and CHANGED (paths tool calls touched, never recomputed). `tests/sidebar_projection.rs` greps the module's source for `Command` or `Transport`, kept outside so the grep cannot trip on its own assertion.
- **CHANGED never claims `+0 -0`.** `diff::counts` returns `None` where diffs cannot be read; the sidebar shows the bare path, not invented zero-line counts.
- **Toasts are driven by the spinner's tick, not a clock.** `App::toast_warning`/`toast_error` raise a toast and write to the transcript in the same call; `warning` notifications are now one of these instead of hand-written status lines. `App::tick` expires it past `expires_at`. Newest replaces oldest. The transcript line outlives the toast, so unread toasts lose nothing.
- **Disconnection stops the spinner without reconnecting.** `App::disconnect` forces the turn back to `Idle`, drops any unanswerable prompt, and is idempotent for the transcript but not turn state. `App::connection_state` reads `ready`/`streaming`/`blocked`/`cancelling`/`disconnected`, the last winning outright. `Transport::alive` catches a dead gateway; a `stream_turn` error is read as transport dying, not ordinary turn failure.
- **The turn indicator moved from the transcript's border to the header** with wordmark, session id and client connection — collapsing to id + state under 60–79 columns. The status bar took over the composer's hint entirely; keybindings show in one place.
- **Out of scope:** sidebar interactivity, reconnection, and any metric the protocol does not carry.

- **Create**: **the ask dialog: a modal, not a status line, and the session it answers with is finally the right one** (Slice 19f, #103). `Notification::Ask` carried `{ session, question, options, default }` since 13b, but `tui.rs` dropped the session and answered with its own — wrong for multi-turn clients. `StreamEvent::Prompt` now carries `session` from the notification and SSE `prompt` frame, and `App::take_answer` returns `(session, answer)`.
- **A queue, not a stack.** `App::pending_prompt: Option<Prompt>` is now a private `VecDeque` behind `App::pending_prompt()` and `App::prompt_queue_len()`. A second `ask` arriving while one is open is appended; the dialog says `1 of 2` once a second is waiting.
- **Selection lives on the prompt**, as an index into `options`, starting on `default`'s index by searching, never assumed first. When `default` is absent, answering requires an explicit choice: contradictions are not guessed at.
- **`Esc` closes the dialog without answering.** The prompt stays queued and the turn stays `Blocked`. `Enter::ReopenPrompt` covers the other half: while a prompt is pending but closed, `Enter` shows the options again — the one thing a modal must never let a keystroke do is confirm a choice nobody saw.
- **Nothing is pre-approved.** No `y`/`n` shorthand or key that confirms without visible selection. A digit jumps to that option's index, 1-based as displayed; the string sent is exact, never lowercased or trimmed. `dialog_keys` in `tui.rs` takes every key ahead of composer and `/`/`@` lists while the dialog is open, so a digit cannot land in a message — except free-text prompts where typing reaches the composer and empty submission sends `default`.
- **The rendering is a pure function, like the transcript's.** `blocks::prompt_dialog` turns a prompt, selection and queue length into `Vec<Line>` with no terminal involved, the same split `blocks::transcript`/`tui::render` uses. The default is marked by a ` default` label and `Glyph::Warning`, and the closing line states plainly that silence takes the default, both surviving `Mode::Mono`.
- **A row in `docs/concepts/security-model.md`** names the tests; `docs_match_config.rs::the_security_model_cites_tests_that_exist` checks the citations resolve.

- **Gate**: **Phase 19's exit criteria are a test now, not a sentence in an issue** (#97). `phase19_gate.rs` drives the turn: user message, streamed answer, three tool calls (one edits a file, one fails), an `ask` answered, a follow-up mid-turn, and a cancel — through the **model**, then renders at 120×32 and 60×20 in both truecolor and `NO_COLOR` on sixteen colours. An umbrella closes when its exit criteria are tested; this repository has twice paid for the other way round: a gate recorded as prose is never run.
- **Its first version passed every probe, which is the part worth recording.** Making `Glyph::ToolFailed` render as `ToolDone` did not fail it, nor did rendering twenty cells wider than the pane. The state comparison included each block's *content*, which already differed, so the glyph was never what the assertion turned on; the fixture's lines were short, so nothing approached the pane. Rewritten with identical content across states and a message long enough to make wrapping load-bearing, the overflow now fails for the right reason.
- **One hypothesis checked and discarded.** `Done { failed: true }` and `Interrupted` both draw `Glyph::ToolFailed`, differing by `removed()` vs `warning()` — erased in `Mode::Mono`. That looked like information carried by colour alone: it is not, because an interrupted call spells the word *interrupted* into its line. `theme::monochrome_still_tells_every_state_apart` catches the glyph collision; the earlier probe simply never ran it, scoped to one test file.

- **Create**: **the turn lifecycle: `Enter` changes meaning while a turn runs, and three signals say so** (Slice 19e, #102). Two of the three things 13b added — `turn/cancel` and `turn/follow-up` — had **no key bound**: `tui.rs` guarded `Enter` on `rx.is_none()`, so while a turn ran the keyboard did nothing except answer pending confirmations. The one capability distinguishing this harness from a plain chat client was unreachable.
- **`Enter` has four meanings and the state picks one.** `Idle` sends a message, `Streaming` steers the turn in flight, `Blocked` answers the confirmation without steering, `Cancelling` does nothing. Extracted into `enter_means`, a pure function of the model. `Blocked` is tested first: a blocked turn is still streaming, so the other order would steer instead of answering. This layers *after* 19d's order — the `/` menu and `@` list take `Enter` first and fall through on an empty list.
- **Steering is refused on REST with a reason a user can read.** The REST surface has no route reaching a turn in flight — a property of the connection, not a missing feature. Sent synchronously, unlike `answer`: `Rest::follow_up` is a refusal with no I/O and `Stdio::follow_up` is one pipe write, so neither blocks the draw loop. The refused message is still recorded, because a transcript showing a refusal without the thing refused is missing half the exchange.
- **Three signals change together, because one signal is one thing to miss.** The caret (`›` → `»`, `>` → `>>`), the composer's label (`message` → `steer this turn`) and the status hint (`Enter to send` → `Enter to steer · Ctrl+C to cancel`). `Glyph::CaretSteering` is a second caret, not a tint: under `Mode::Mono` every role is `Color::Reset`. `monochrome_still_tells_every_state_apart` excludes both carets, so `the_two_carets_are_told_apart_in_both_vocabularies` keeps that exclusion a judgement.
- **The spinner advances on the poll tick, not on an arriving delta.** `text-delta` is documented as one per completion, not per token, so an animation driven by arrivals would sit frozen through the long wait it exists to reassure about. Probed by pinning the frame to a constant, which fails the test.
- **`Ctrl+C` and `/cancel` meet at one sender.** `/quit` already had the shape: the model records intent and the event loop performs it. `App::cancel` raises an ask it refuses to raise twice, and the loop drains it — so `/cancel` acts without `App` learning what a transport is, and a second `Ctrl+C` cannot send a second cancel. The partial answer **stays**, because cancelling finalizes with what is in hand.
- **`Ready` stopped meaning "needs no transport".** It meant both by coincidence — the only commands that acted happened to need neither. `/cancel` separates them, so `exactly_the_commands_that_need_no_transport_are_ready` is now `exactly_the_commands_that_act_are_ready`. Two tests pinning apologies were rewritten: one asserted `#157` in the status line, the other that the UI printed `#161` — both pinned explanations for limitations that no longer exist.

- **Create**: **the client can create a session and cancel a turn** (#157). `Command::SessionCreate` and `Command::TurnCancel` were in the protocol since 13b; `Transport` carried `stream_turn`, `answer`, `follow_up` and `describe`, so two of six `/` commands were listed as *pending*.
- **Cancelling is not one behaviour.** Over REST + SSE, cancelling drops the stream — `rpc.rs` reads a closed connection as `Flow::Stop`. Over stdio the connection outlives the turn, so a real `turn/cancel` is the only way. One method, two honest implementations. `Rest` parks a `try_clone` of the live turn's socket so `cancel` can shut it down; a `ClearLiveOnDrop` guard clears it on every exit, and the socket is stored **before the request is written**, so a cancel racing the start still has something to close. Cancelling with nothing running is a stated error.
- **The test proves the turn stops, not that a message was sent.** A fake server streams `delta` frames forever; the turn runs on a background thread, `cancel` is called, and `stream_turn` must *return* within five seconds. Probed by making `cancel` report success without tearing the socket down, which hangs to the timeout.
- **`create_session` over stdio reads its own answer, a constraint.** `answer` and `follow_up` do not, because the turn thread owns the reader; this one must, so it is valid only when no turn is streaming, costing a frame from the turn thread if violated.

- **Build**: **the release can sign itself; the key is the one thing left** (#93). `release.yml` signs with minisign 0.12, pinned by version **and** sha256 — the tool that establishes provenance for every artefact, which fetching over TLS with no checks would trust to the CA system.
- **Components are signed in the `build` job, archives in `release`, ordered by constraint.** `registry_index::signature_beside` reads `<component>.minisig` while building each entry, so late-signed components would show `"signature": ""` in the index. **Per file, never per archive**: `ext install` verifies `.minisig` beside component *and* manifest, so a component extracted from a signed tarball arrives unsigned and is refused; signing archives only would leave first-party components uninstallable. Signatures ride through to release assets and `_site/ext/`, where `ext install` resolves them as siblings of the component URL.
- **No key, no signature, and it says so.** `MINISIGN_SECRET_KEY` is unset today; generating a signing identity is the owner's work and the private half must never pass through a build log. Both signing steps skip with a `::warning::`, shipping an unsigned release that reports itself unsigned and an index with `"signature": ""`. The secret reaches each script as an **environment variable**, never interpolated into the script text.
- **`install.sh` now says what its checksum proves and what it does not.** It downloads `SHA256SUMS.txt` from the same release as the bundle — the check catches corruption but establishes nothing about provenance. It deliberately does not verify the signature: minisign is on few machines, and an installer that verified only when present would report success for two quite different situations. Verifying by hand is one documented command.
- **Still open.** No key exists; nothing is signed; the workflow half never ran. #93 stays open on that handover.

- **Fix**: **`release.yml` fetched WIT deps before installing the tool that fetches them, and `|| true` hid it** (#166). Three defects in four lines: `Fetch WIT spike deps` ran *before* `Install wkg`, so on a clean runner `wkg` did not exist; both steps ended in `|| true` so `wit/spike/deps` was silently never populated — a step that does not run looking exactly like one that passes; and the install was `cargo install wkg --locked`, which pins wkg's **own `Cargo.lock`** — so the release leg resolved a different tool from the leg that validates `wit/wkg.lock`. Nobody noticed because `release.yml` never ran.
- **Order fixed, `|| true` gone, pinned prebuilt used.** The fetch now calls `make -C src/extensions spike-deps` — the target a developer calls, so the two cannot drift — and is allowed to fail, because a guest needing those deps will not build anyway.
- **The "twin in `ci.yml`" rule is now checked, not asserted in prose.** `versions.mk` says every pin has a twin; nothing verified it, which is how #166's `wkg` drifted. `every_tool_a_workflow_pins_matches_versions_mk` reads `versions.mk` and every workflow and fails when a workflow installs a version the pin does not name — probed in both directions. Comment lines are skipped deliberately.

- **Verify**: **the release publishes the registry where `config.yaml` says it is** (#139). `release.yml` generates `index.json` through `make registry-index` **by name** (not a copy in the workflow), uploads it as an artifact, and the `release` job copies it to `_site/index.json` with components at `_site/ext/`. What was missing: three paths had to agree, and **only a comment said so**.
- **That is the shape #130 and #131 cost this repository**, and it matters more here because the mistake is unobservable until a tag exists. `the_release_publishes_the_registry_where_config_yaml_says_it_is` reads both files and holds them together; probed against three realistic mistakes and catches all three. The deploy itself remains unproven until the first tag.

- **Fix**: **`ext install` staged unverified downloads in a predictable world-readable `/tmp` path, and two installs in one process fought over it** (#168). `install_from_url` named its staging directory `jk-ext-fetch-<pid>` and `remove_dir_all`s it at **both** ends, so two installs wiped each other's half-fetched files — the failure was a `.minisig` downloaded then deleted by a neighbouring thread. Same collision shape as #165, in production.
- **The half that outlives the flake is the path itself.** What lands there is a component, its manifest and signatures **before any verification**, then read back out to be checked — at a world-readable name anyone can guess in `/tmp`. The repository already had the answer: `wasm_cache::ensure_private_dir` creates the compile cache `0700`. That argument is stronger here. The staging directory is now per call and private. `ext_install` failed intermittently before and passes 21/21 across eight consecutive runs now.

- **Fix**: **a tool call and its result now read the same over REST as over stdio** (#161, #162). `Notification::ToolInvoked` carried `{ id, name, arguments }` and the SSE `tool` frame carried two of three, so a client with `--addr` could not render the collapsed line naming *what a call did*. A connection detail was deciding what the transcript could say.
- **The other half is that nothing said a tool call had failed.** `ToolOutcome` was `{ tool_call_id, content }` and both frames carried content and nothing else — a failed call and a successful one were the same shape. The only way a client could tell was to match the core's sentences: ``tool `X` error:``, ``tool `X` trapped``, `tool call denied:`. `failed` is now a field on `ToolOutcome`, `Event::ToolResult` and both wire frames, and `blocks.rs`'s prose matcher is deleted.
- **A guest interceptor cannot launder a failure into a success, needing a guard.** `wit/interceptor.wit`'s `tool-outcome` has no `failed` field deliberately: rewriting `content` is a `tool-result` interceptor's business, not whether the call failed. A guest's `Replace` arrives back as `failed: false` whatever the truth was, so a denial could return drawn as a success. `interceptor_host::preserve_tool_result_failed` restores the host's verdict across the boundary.
- **The test is that the two surfaces agree.** They had already drifted once (#161). `every_turn_event_frame_fits_its_notification` only checked that a frame's keys reach its notification. With that asymmetry gone, `tool_invocation_frames_and_notifications_carry_exactly_the_same_fields` holds the stronger claim. An older core sending no `failed` key parses as `false`, not as a malformed frame: refusing would turn a version disagreement into a broken turn.
- **What the flag bought, as the test that replaced the corpus.** `every_failure_the_core_writes_is_recognised` pinned six sentences the matcher knew. Its worries are now unreachable rather than guarded, so the new test points fixtures the opposite way — a successful call whose output quotes `tool call denied:`, and a failure phrased in words no list would hold. A prose matcher gets both wrong; reading the flag cannot.

- **Fix**: **two `@`-completion tests shared one temp directory, so the gate went red one run in six** (#165). `paths::tests::tree` named its fixture directory after the process id and `SystemTime::now().as_nanos()`, which reads unique but is not: **macOS's clock has microsecond granularity**, so `as_nanos()` always ends in three zeros. Two tests calling `tree()` together got the same name and directory — one test's fixtures landing in another's tree, and the first finisher deleting the other's root mid-walk.
- **A process-wide atomic counter replaces the clock**, so collision is impossible by construction. The fixture clears any tree a previously panicking run left behind. It failed one run in six before and passes 20 consecutive runs now. Worth the entry because of *which* assertion it was breaking: intermittent failures make `make gate` results probabilistic.

- **Fix**: **the first command on every entry point now works** (#126). `README.md`, `docs/quickstart.md` and `pages/index.md` all opened with an installer that 404s: the very first instruction a new reader met ended in `error: could not determine latest release tag` and exit 1. - **Feature**: **`registry-mcp` speaks MCP over a stdio child, so the inbound ecosystem port reaches the servers the ecosystem actually ships** (Slice 18c-2, #110). It spoke SSE and streamable-HTTP only, because `host-process` ran to completion — and most MCP servers distributed today are stdio processes. A `Server` now carries a `Wire`, HTTP or a child handle, and one dispatch point makes `tools/list`, `tools/call` and `reconnect` transport-agnostic rather than written twice.
- **The framing is where the care went.** Newline-delimited JSON-RPC, accumulated until a newline — a read is bounded by the host's `output-cap`, so one reply can arrive across several and treating a read as a message would truncate anything larger than an operator's number. An empty read means "nothing arrived in that window" and **not** EOF; liveness is a separate question asked of `is-running`, and conflating the two gives either a spin or an early stop.
- **A server that misbehaves is a missing capability, not a broken agent.** One that never answers is given up on after ten seconds and reported down; one that answers something that is not JSON fails on the parse. The turn runs either way, which is what the tests assert — with a wall-clock bound, because a client that hung forever would also "produce no tools" and a test satisfied by that is satisfied by the bug.
- **It needed a second interface bump, 0.2.0 → 0.3.0, for a reason the issue did not anticipate**: `mcp-registry-world` did not import `host-process` at all, so "`registry-mcp` gains `transport: stdio`" was never a guest-only change. The host half of that interface also existed only for `tool-*` guests, so the child table became a shared `host_process::Children` rather than a second copy — #109's lifetime guarantee has to hold identically for a registry instance, and a guarantee implemented twice is one that will eventually be implemented once.
- **A stdio entry names a granted child, never a command.** The operator writes the server once in `execution.long-lived` and once in `servers`, and an extension cannot introduce a program — only ask for one already named. Such a child is confined like any other command, so **by default it has no network**, which `configuration.md` now says out loud: an MCP server that calls an API will otherwise fail in a way that looks like the server being broken.

- **Feature**: **`host-process` can hold a child open, and the grant names processes rather than permitting spawning** (Slice 18c-1, #109). `exec` runs to completion, so the core could not hold a stdio MCP server, an `lsp-*` or a browser driver. `spawn`/`write-stdin`/`read-stdout`/`is-running`/`kill` do, behind `execution.long-lived: [ { name, command, args } ]` — a guest asks for a **name** and the host supplies the command, so there is no path by which a string the guest chose becomes a program. That makes it **narrower** than `execution.enabled`, not a wider version of it: `enabled: true` alone grants none, and an entry missing `name` or `command` is skipped rather than guessed. No consumer yet; `registry-mcp` using it is #110.
- **A `u32` handle rather than a `resource`, against the slice's own scope line.** That line wanted the lifetime to be "the component model's problem rather than a bookkeeping convention" — but the host must leave no orphan when an instance stops or the runtime drops, so it owns the lifetime either way, and the table it keeps to enforce that is the same table that validates a handle. What remained was: the repository's first resource, against two existing handle precedents, for the gain of not validating an integer it already tracks.
- **Confinement is reused, not restated.** `exec`'s confine-then-configure sequence became `ProcessRunner::prepared`, and both paths go through it — they differ only in what they do with the `Child`. A child that outlives its call is *more* exposed than a one-shot command, so the one place that decides how a command is bounded had to be the one place both reach it through. `read-stdout` gets a reader thread rather than a poll: the core is single-threaded and a pipe read blocks, so a child that says nothing — which a stdio server does whenever it has no reply — would otherwise hang the runtime and take the turn, the transport and every other instance with it.
- **The lifetime is proved by looking for the process.** `LiveChild`'s `Drop` kills what it holds, and the child is owned by the per-instance `ToolHost`, so it dies whether the instance stops cleanly, errors, or goes down with the runtime. The test spawns a child that reports its own pid, deliberately never kills it, and checks the pid is gone once the runtime has dropped — with `sleep` rather than `cat`, because a `cat` exits on its own when its stdin pipe closes and the test would have passed without the host killing anything.
- **The first interface version bump: `jan-klod:interfaces` 0.1.0 → 0.2.0**, minor, across all 15 `wit/*.wit`, the host's `API_VERSION` and 18 regenerated manifests. `proc-error` was left alone deliberately — adding a case to an enum is a *major* bump by `contracts.md`'s own table, which pre-1.0 means `1.0.0`, so `read-stdout` reports "nothing arrived" as an empty string and `is-running` answers liveness separately.
- **The bump exposed two fixtures that had encoded the version they were testing against**, and both then passed for the wrong reason: `manifest.rs`'s version-refusal test rewrote `0.1.0` → `0.2.0` to build an "incompatible" component, which became a no-op and left it compatible; `manifests-selftest.sh` did the same in `sed` and reported that a disagreement had been *accepted* when in fact its tamper had stopped tampering. Both now derive the live version and rewrite to a distinct **major**, incompatible under both the pre-1.0 rule and the one after it.

- **Feature**: **`session/get` now carries the seq that `session/fork` takes, so a client can fork at a point it read** (#106). Fork names an event sequence number; the only command that reads a session back returned `{role, content}` with no position on it. So fork was reachable only by a caller that already knew the log's internals — which no client does. `jan-klod-ui` could not offer "fork from here" because it held the messages and not their places, and Phase 19's dialog slice excluded fork for exactly this reason.
- **The seq is exact, not a convention.** `projection::transcript` is a `filter_map` per row and `message_for` takes one `Record` returning at most one `Message` — never a fold — so a message comes from precisely one event and "the seq of a message" needs no rule about which of several it means. `at-seq` is inclusive, so forking at a message's seq yields a child whose transcript ends with that message, which is what the new test asserts rather than assuming. The seqs are **sparse**: an ask, an answer, a text delta project to no message and still consume a position, so seq is a log position and not an index into the list.
- **The read shape is in the contract now, which it never was.** The protocol crate typed `Command`, `Notification` and `HelloResult`; the `session/get` *result* was untyped JSON assembled in `serve.rs`, reaching no schema and no generated client. Adding a field to it would have satisfied the issue's "the schema is regenerated" line while changing nothing in the schema — the same defect one level up, since the commands were declared ahead of any transport precisely *because the schema is what non-Rust clients generate from*. `SessionGetResult` and `TranscriptMessage` are now declared beside `HelloResult`, and the integration test parses the real served bytes into that type, so the declaration and the response cannot drift.
- **The test forks the way a client has to.** It reads a seq out of `session/get` and uses nothing else — reaching into the store for one would have reproduced the bug inside the test and still passed. Probed by dropping `seq` from the payload, which fails it. Found on the way: a `session/get` queued behind a `session/message` is refused mid-turn, the same `409` REST gives, so the exchange has to be split the way the existing fork test already splits its own.

- **Create**: **the macOS half of the sandbox is CI-verified for the first time** (#95). Every job in `ci.yml` is `ubuntu-latest`, and every Seatbelt test is `#[cfg(target_os = "macos")]`, so a regression in the macOS backend landed green — while Landlock had the mirror problem, verified on every push and invisible on the machine this repository is developed on. `ci-macos.yml` runs the Seatbelt suite plus the core unit tests on `macos-latest`. Both backends are now guarded; the asymmetry that remains is *when*, not whether.
- **It is narrow on purpose, and the reason is money.** This repository is private, and GitHub bills a macOS runner minute at ten Linux minutes, so a second full `make gate` would cost 150–250 billed minutes per push. The job is filtered to the sandbox sources, the sandbox tests, `wit/host-process.wit` and its own workflow, plus `workflow_dispatch`. `.github/AGENTS.md` records the 10× reason, so widening it is a decision rather than a reflex — and states the cost of the filter plainly: a change that breaks Seatbelt without touching those paths still lands green.
- **A separate workflow rather than a fourth job, and that is forced.** `paths` is a trigger filter on the *workflow* (`on.<push|pull_request>.<paths>`); there is no per-job equivalent, so putting the filter in `ci.yml` would have gated `lint-test`, `harness` and `supply-chain` behind it too.
- **Its guard had to be taught to report its own failure before it could report anything else.** The first version — `n=$(cargo nextest list … 2>/dev/null | grep -c …)` — died under `bash -e` before the echo that would have explained why, with the compile output discarded. Rewritten, it immediately showed the real cause, which was the colour trap fixed in #123 one layer down.

- **Fix**: **`main` is green again, and what had been red was never what the failing job said.** `ci.yml` failed on every push from `c47eab0` onward. The visible message was `make gate`'s zero-test guard reporting `resolves 0 test(s)` — but that guard landed *later* (`ad4eecd`) and was itself broken: `ci.yml` sets `CARGO_TERM_COLOR: always`, nextest honours it even into a pipe, and the guard's `^jan-klod-host::it ` anchor cannot match a line that begins with an SGR escape. 172 matches uncoloured, 0 coloured, on one tree. So a guard that failed closed sat in front of the real failure for seven runs, and the log said "the integration suite compiled zero tests" while four known-failing tests waited behind it (#123).
- **The local gate could not have caught either.** `.github/hooks/pre-push` runs the same `gate-push` target CI runs, and the hook's own comment says the sequence lives in the Makefile "so this hook cannot drift from CI" — but it ran that sequence in a different *environment*, uncoloured, and passed on every push CI then failed. `CARGO_TERM_COLOR` now comes from the root Makefile, defaulting to CI's `always`, so both sides parse tool output the same way. Chose parity in the stricter direction over deleting the variable from `ci.yml`: both make the sides agree, only this one makes the local gate exercise the colour path.
- **Fix**: **the four `execution_config` tests that were actually red: a confined command could not run under `cargo test` on Linux, and it was the wrapper, not the sandbox** (#124). `LandlockBackend` confines by re-executing `current_exe()` with a `confine` subcommand — `jan-klod-gateway` in production, the *test binary* under nextest, which answers `error: Unrecognized option: 'writable'` and exits 101. Every command then failed in a way that reads exactly like Landlock refusing it. `sandbox_landlock.rs` documents this trap and sidesteps it with `LandlockBackend::new`; a test that boots a real `Runtime` could not, because the backend is resolved inside `open_process_runner`. `Runtime::with_sandbox_wrapper` is that seam. Deliberately not a `config.yaml` key — an operator who could name the confinement wrapper could name one that confines nothing — and it overrides only *which* binary is re-executed, never *whether* confinement happens: a wrapper that is not there yields no backend, the mode downgrades, and the boot line says so.
- **The shipped runtime was never affected**, which is worth stating because the issue was filed `P0` and read like a sandbox escape. `open_process_runner` only ever runs inside `jan-klod-gateway`, where `current_exe()` is the binary that handles `confine`; the only other shipped binary is a client that never boots a `Runtime`. What was broken was the ability to *test* the config-built path on Linux.
- **Test**: **a confined command that is expected to succeed, which is the assertion that was missing.** For seven runs every Linux signal was consistent with "Landlock denies everything": the denial tests passed, and #82's confinement test passed too — it asserts a command *cannot* write outside its workspace, which a wrapper that never starts satisfies for free. `a_confined_config_built_runner_can_still_write_inside_the_workspace` is the other half, and the pair is what separates confined-and-working from confined-and-broken. Probed by revoking the grant it depends on (`writable: []`), which fails it; both are cited on `security-model.md`'s command-effects row as the runner *the boot path builds*, distinct from the ones its other citations assemble by hand.

- **Test**: **the `execution:` block is now verified from config to a running command, including the confinement — the last of #82's four gaps.** `Runtime::open_process_runner` is the only thing that turns `execution:` into a `ProcessRunner` in production, and no test reached its enabled branch: `host_process.rs`, `tool_git.rs`, `sandbox_seatbelt.rs`, `sandbox_landlock.rs` and `sandbox_boundary.rs` all built a runner by hand. The assertions were real and were not attached to the code that runs. `execution_config.rs` now boots a real `Runtime` from a config fixture and drives commands through `tool-proc-probe` across the Component-Model boundary: the switch, the three values (`timeout-secs`, `output-cap`, `env-passthrough` — the last asserting that an *ungranted* name does not arrive, since "passthrough works" and "passthrough is a grant" are different claims), the three denials, and now the confinement.
- **The confinement half is the one an operator most needs to be true, and it was the claim with nothing behind it.** The enabled branch ends in `match (effective.mode, backend)`, over a comment reading "the runtime cannot report `Os` while running commands unconfined". Nothing checked it on any platform. Two tests do now, in the shape `sandbox_seatbelt.rs` established: an unconfined control under `mode: approval-only` whose escape write must succeed, and — with **no `sandbox:` block at all**, which is what an operator gets for asking for nothing — the same write, which must be denied. The observation is a word reaching the model (`echo x > outside && echo wrote`) rather than a file on disk, because the harness removes its temp tree when the turn ends.
- **Probed in both directions, since a green test proves nothing about what it would catch.** Inverting the wiring match (`Os` → `ApprovalOnly`) fails *both* new tests, each in its own direction — the control's write denied, the confined write allowed — so neither is passing incidentally. Replacing the match with an unconditional `runner` fails only the confined test and leaves the control green, which is what separates the pair from a single fact asserted twice. `lib.rs` is byte-identical afterwards.
- **The confined half is gated on `sandbox::host_backend()` being present, not on `#[cfg]`.** `mode: os` downgrades to approval-only where there is no backend, so without one that test would assert the opposite of what it says; and the Linux backend can be absent at runtime on a kernel without Landlock, which a `cfg` would not notice. The control is deliberately platform-independent, so a machine with no backend still checks one side rather than reporting green having checked neither.

- **Fix**: **the egress policy now connects to the address it classified** (#108, `d413067`). `EgressPolicy::check` resolved a host and approved it; ureq then resolved the same name again on its way to the socket. A name whose answer changed in between was **checked as public and connected to as private** — the care the policy takes over address classes undone by the second lookup. `check` now returns the addresses it classified and `exchange` hands them to the agent as a fixed resolver, so there is one lookup and the connection lands where the check looked. This is the other half of #107 (`2026-09-11`), which fixed the policy being applied to the URL a caller named rather than the destination actually contacted; the two are one story about the same function, and until now only the first half was written down.
- **Pinning the address does not disturb TLS or virtual hosting**, which is what makes it safe to do at all: `Host` and SNI come from the URI's authority in ureq, not from the address, so the pinned agent differs from the previous one in its resolver and nothing else.
- **Two paths resolve nothing and are deliberately left unpinned.** An address literal consults no resolver and has no answer that could change. A **granted origin is trusted by name, not by address** — `network.allow` and the origins `config.yaml` names are the operator saying *this endpoint*, and re-deciding where it may point would second-guess them. `docs/concepts/security-model.md` carries that as a stated limitation rather than an omission.
- **The cost is a semver exemption, and it is commented at the call site.** `Agent::with_parts` and `Resolver` live in `ureq::unversioned`, which ureq's own docs exempt from semver. A minor bump can break the call — a compile error rather than a silent reopening, which is the right failure — so the next upgrade meets the constraint instead of discovering it. This entry also supersedes two earlier ones that describe the DNS-rebinding window as open; those stay as written, because they were true when written and a changelog that edits its own history is not a record.

- **Implement**: **Standing permission decisions — `always` / `never`.** `interceptor-permission` asked the same question on every dangerous call, which is the failure mode that gets a security boundary switched off entirely: a gate people disable protects nothing, so ergonomics here *is* a security property. The confirmation now accepts `always` and `never` alongside `yes`/`no`, recorded per **kind of action** and consulted before asking again. The scope key is the discriminator that matters — `op` for a multi-op tool (`fs:write`), the *program* for a command runner (`shell:cargo`, from `cargo test --workspace`), the bare name otherwise — so approving writes never approves deletes, and approving `cargo` never approves `curl`. Keying on the whole argument set would never match twice; keying on the tool alone would be a blanket grant.
- **Decide**: **Standing decisions are run-scoped, never persisted, and never cover a scope escape.** Three constraints keep the convenience from eroding the boundary. (1) They live in `host-storage`, which for an interceptor is memory owned by that instance — restart the agent and it asks again, because a permission boundary must not quietly become permanently open on the strength of one click last week. (2) `Concern::EscapesScope` is **un-rememberable**: "always allow writes" is about writing files, not about writing `/etc/passwd`. This is why `Policy::review` runs the **scope check first** — if a path escape were reported second, `{"op":"write","path":"/etc/passwd"}` would surface as the rememberable `DangerousOp` and a prior "always allow `fs:write`" would wave it through. (3) Every unreadable state — a storage error, a missing entry, a stored value that is not exactly `allow`/`deny` — falls back to asking; nothing can turn a broken read into an approval, and a failed *write* still lets the current call proceed (the user is simply asked again next time) so failing to persist a convenience never fails the security decision.
- **Implement**: **`tool-git` — read-only repository inspection.** New Rust guest in [src/extensions/tool-git/](../src/extensions/tool-git/), the 16th first-party component. The fleet could read, find, grep, and edit files but was blind to version control: checking its own diff meant enabling `tool-shell`, i.e. paying arbitrary command execution for `git status`. One tool, `git`, with five ops — `status`, `diff` (`staged`?, `path`?), `log` (`count`?, `path`?), `show` (`rev`), `branch`. The guest builds the argv itself from a closed op set, so the only program it can run is `git` and the only subcommands are those five. **There is no `commit`/`checkout`/`reset`/`push` — not disabled by policy, simply not expressible in the contract**, which is the difference between a capability granted and a capability *shaped*. Caller-supplied `rev`/`path` are validated (no leading `-`, restricted charset, length cap) and a pathspec is passed after `--`, because those two values are the only argv entries the model controls and `--upload-pack=…`-style options are how a value becomes a command.
- **Decide**: **Reading a repository is not inherently side-effect-free, so every invocation is hardened.** A checkout is data the agent did not write, and git treats parts of it as *configuration*: `.git/config` can point `core.fsmonitor` at a command that runs during `git status`, `core.hooksPath` at a directory of scripts, and `.gitattributes` can name external diff/textconv drivers that run during `git diff`. "Show me the diff" on a hostile repo is therefore a code-execution path. Every call carries `--no-pager --no-optional-locks -c core.fsmonitor=false -c core.hooksPath=/dev/null -c protocol.ext.allow=never`, and the diff-shaped ops add `--no-ext-diff --no-textconv`. Aliases need no guard — git refuses to let an alias shadow a real subcommand, and only real subcommands are emitted. This is the fail-closed boundary applied one level in: the sandbox already stops the *guest* from doing anything unexpected; this stops the *repository* from doing so.
- **Fix**: **`workspace:` and `execution:` were undocumented keys the core actually reads.** `Runtime::open_workspace`/`open_process_runner` read top-level `workspace:` and `execution:` (`enabled`/`timeout-secs`/`output-cap`) from config, but neither appeared anywhere in the shipped [config.yaml](../config.yaml) — so a user who enabled `tool.shell` (as its own comment invited) got a tool that failed closed with nothing explaining why, and the deployment-wide execution switch was invisible. Both are now written out with their defaults and their default-deny semantics stated. Same class as the earlier "shipped config gave a fresh install no tools" fix: the core's real contract has to be legible in the file users edit.
- **Implement**: **`tool-fs` `grep` searches a directory tree, not just one file.** Previously `grep` took a single `path` and returned `lineno:line` — so "where is this symbol?" cost the model a `find` plus a `read` per candidate, which is the sort of turn budget a small model does not have. `grep` now defaults `path` to the workspace root and searches the whole tree when `path` names a directory (probed by whether `list-dir` succeeds — `host-fs` has no `is-dir`, and widening the contract for a two-branch dispatch is not worth it), with an optional `glob` to narrow which files are read. Tree hits are prefixed `path:lineno:line`; a single-file `grep` keeps its old `lineno:line` shape. Bounded like the walk it rides on: 400 matches, then `…[partial: stopped at the match cap]`, and a walk bound is reported separately from a match bound so the caller can tell "too many hits" from "did not finish looking". A file that cannot be read (binary, not UTF-8, gone mid-walk) is skipped — one bad file must not cost the caller the other 200 results.
- **Refactor**: **Shared `guest-fs` library for the `host-fs`-routed guests.** `truncate` was duplicated byte-for-byte in `tool-fs` and `tool-edit`, and tree-grep would have made `tool-find`'s glob matcher and bounded walk a third copy. All of it — the output cap, the glob matcher, the bounded walk, and the cost bounds (`MAX_VISITS`/`MAX_DEPTH`/`MAX_RESULTS`/`MAX_OUTPUT_BYTES`, `PRUNED_DIRS`) — now lives in [src/extensions/guest-fs/](../src/extensions/guest-fs/), a workspace member that is **a library, not a component**: it holds no WIT bindings and imports no capability, so guests stay separate sandboxed components that merely compile the same tested logic in. Cost policy now has one place to change rather than three that can drift. [src/extensions/Makefile](../src/extensions/Makefile) gained a `LIBS` list so such crates are tested but never built to wasm or staged in `ext/`.
- **Fix**: **The roadmap claimed `tool-web-search` was built; it does not exist.** No `web-search` guest is in the tree (`config.yaml` carries only a disabled config placeholder) — the Phase 8 fleet table's *(built)* marker was wrong. Corrected, and `bash/shell` marked *(built)*, which it actually is.
- **Implement**: **`tool-find` — glob discovery over the workspace tree.** New Rust guest in [src/extensions/tool-find/](../src/extensions/tool-find/), the 15th first-party component, closing the fleet's discovery gap: `tool-fs` could `read`/`grep` a path it was *given* and `tool-edit` could patch one, but nothing could **enumerate** paths — a fresh session had no way to learn what files exist short of guessing them. One tool, `find`, taking `pattern` (+ optional `path` root): `*`/`?` match within a segment, `**` spans directories, and a pattern with no `/` is expanded to `**/<pattern>` so `Cargo.toml` finds the file wherever it lives (strict glob semantics would mean "repo root only", which is never what the caller meant). The walk is **guest-side over `host-fs`'s `list-dir`** — it sees exactly what the jail exposes, so no host-side directory-walking capability had to be granted.
- **Decide**: **A glob's cost is set by the tree, not the argument — so every dimension of the walk is bounded and a bound that bites is *said*.** `**/*` in a monorepo is one token from the model and unbounded work for the runtime, the one file operation where that asymmetry exists. Four caps: 20 000 entries visited, depth 24, 500 results, 64 KiB output. Heavy build/vendor trees (`.git`, `node_modules`, `target`, `.venv`, `__pycache__`, `.jj`) are pruned unless the pattern names one literally (`target/**/*.rs` opts back in). When a cap stops the walk the result appends `…[partial: stopped at the <bound>]`, and a byte-capped list appends the count omitted — a truncated tree must never read as an exhaustive one. An unreadable subdirectory is skipped, not fatal; only a root the jail refuses is an error.
- **Fix**: **The default boot plan (`jan-klod <config> <ext>` / `make run`) could not start any tool, registry, or interceptor.** `Runtime::start_all` instantiated *every* compiled component through the neutral `extension-world` linker, which grants only `host-log`/`host-config`/`host-http` — so a `tool-*` guest (imports `host-fs`/`host-process`), `registry-*` (`host-fs`/`host-event`), or `interceptor-*` (`llm-provider`) failed at instantiation. - **Verify**: 14 native unit tests for the matcher and walk (segment-bounded `*`, `**` spanning zero-or-more segments, `?`, backtracking `*` on repeated prefixes, slash-less expansion, sorted recursive results, root-relative matching with workspace-relative output, prune-unless-named, unreadable-dir skip, result cap, no-match line, partial note, byte-cap truncation count); a new CM-boundary integration test [src/core/host/tests/tool_find.rs](../src/host/tests/it/tool_find.rs) drives recursive glob → pruned-dir exclusion → opt-back-in → scoped `path` → no-match → **`path: ".."` denied by the jail**, plus default-deny with no workspace. `cargo clippy -p tool-find --all-targets` clean; `tool.find` enabled in the shipped `config.yaml`; `make run` against that config now starts all 8 enabled extensions (the boot-path fix below), and `make gate` is green.
- **Implement**: **`tool-edit` — hash-anchored partial file edits.** New Rust guest in [src/extensions/tool-edit/](../src/extensions/tool-edit/), the 14th first-party component and the edit-reliability lever [small-model-harness.md](concepts/small-model-harness.md#edit-reliability-tool-edit--built) had specified but nothing implemented: until now the only way to change a file was `tool-fs`'s whole-file `write`, which is exactly the re-emit-the-whole-file failure mode small models fall into. One tool, `edit`, with three ops — `view` renders each line as `anchor|lineno|text`; `replace` swaps an anchor span (`end` defaults to `start`; empty `contents` deletes); `insert` places text `before`/`after` an anchor. `contents` must be *present* on `replace`/`insert` even when empty, so an omitted key cannot silently delete a span. An **anchor** is `fnv1a32(lineno \0 text)` in 8 hex, so it validates a line's position *and* content together: if the file changed since the model viewed it, no anchor resolves and the edit is **rejected with nothing written**. A hash collision resolves as ambiguous and is rejected the same way — a collision costs a retry, never a bad write. All I/O goes through the path-jailed `host-fs`, so the guest never touches the raw filesystem.
- **Decide**: **Recoverable edit rejections return `ok`, not `tool-error`.** `tool-callable`'s `tool-error` enum carries no message, and `tool_host` surfaces it to the model as the bare `tool \`edit\` error: ExecutionFailed` — from which a model cannot self-correct. Stale/ambiguous anchors therefore come back as an `ok` result reading `REJECTED (nothing was written): … Run op=view again and retry with fresh anchors.` `err` stays reserved for malformed arguments and `host-fs` failures. Fail-closed is about the *write*, which does not happen either way; the error channel is chosen for recoverability. This kept `wit/tool-callable.wit` unchanged.
- **Fix**: **The shipped `config.yaml` gave a fresh install no tools at all.** [docs/quickstart.md](quickstart.md) claimed "by default, only file access is enabled", but `extensions.tool` held only a disabled `web-search` placeholder — Phase 8's `tool-fs`/`tool-shell` were never added — and `interceptor.tool-selector` was disabled, so even an enabled tool is never advertised to the model at `select-tools`. Added `tool.fs` (enabled), `tool.edit` (enabled), `tool.shell` (disabled), and enabled `interceptor.tool-selector` + `interceptor.permission`. Net default posture: the agent can read and edit its workspace, every write is confirmed first, and shell execution stays opt-in — v0.1.0 completion criteria 2 and 3, which the shipped config did not actually meet.
- **Verify**: 12 native unit tests for the patch logic (anchor uniqueness across duplicate lines, span replace, delete, insert before/after, stale-anchor rejection, `end`-before-`start`, trailing-newline round-trip, output cap); a new CM-boundary integration test [src/core/host/tests/tool_edit.rs](../src/host/tests/it/tool_edit.rs) drives view → replace → **stale-anchor rejection with the file byte-identical** → re-view → insert against a real path-jailed workspace, plus default-deny with no workspace. `cargo test --workspace` in `src/core` green; `cargo clippy -p tool-edit --target wasm32-wasip2 --all-targets -D warnings` clean; `make gate` green.
