# Changelog

## 2026-08-12

- **Fix**: **the suite was not slow — a test was silently waiting out a three-minute timeout.** I set out to speed up `make gate`, having said it took nine minutes. It does not: a clean run is 2m15s. The nine minutes came from `auth.rs`, which on some runs took **360 seconds** and on others one second, passing either way. 360 is exactly 2 × the 180-second confirmation timeout. A test whose answer goes astray does not fail — the wait expires, the prompt's default is taken, and for the permission gate that default is a denial, which is what the assertions already expected. The suite looked intermittently slow rather than intermittently broken, which is a much easier thing to ignore.
- Two changes make it loud. The confirmation wait is now overridable with `JK_ANSWER_TIMEOUT_SECS`, and the prompt tests set it to five seconds — three minutes is right for a person and disastrous for a test. And `auth.rs` was **discarding the response** to the very answer the rest of it depended on; it now asserts that answer was accepted, so a lost one fails in ten seconds with a diagnostic instead of stalling and reporting success. Verified by deleting the answer: fast red, correct message.
- **Not fixed**: the underlying race. Six consecutive isolated runs were clean, so I have not reproduced it and will not claim a cause. What changed is that the next occurrence will be a visible failure rather than three quiet minutes. Worth noting it may not be test-only — if an answer can be lost under load here, a user's answer can be lost too, costing them three minutes and a denial.
- **Correct**: my own measurement method was wrong before the finding was right. I timed `make` targets and blamed a per-guest `cargo test` loop (0.6s warm) and a make jobserver (disproved: `MAKEFLAGS=-j1` ran in 48s). The number that mattered — 47s versus 3m31s for identical work — was visible in the first measurement and I read it as noise.

- **Fix (security)**: **Every guest was handed the host's standard input.** All six `WasiCtx` sites called `inherit_stdio()`, so a component could read the terminal the gateway runs in. `jan-klod-gateway ask` runs in the user's shell, which makes that the user's keystrokes — including the answer being typed at a permission prompt, the one input whose entire purpose is to be a human's decision. Now `inherit_stderr()`: a guest keeps a channel for panic messages, which is what makes a broken component diagnosable and grants no authority, and gets no stdin at all.
- **Test**: **a component that tries to escape, so the sandbox is demonstrated rather than assumed.** Every other guest is cooperative — it asks through a typed import and stays inside it — which makes for poor evidence, and is exactly why the SSRF guard sat inside `tool-fetch` for weeks: nobody had written the component that skips the check. `tool-escape-probe` skips all of them. It opens a TCP socket with `std::net`, reads `std::io::stdin`, and calls `std::fs::read_to_string`, all plain Rust, because an attacker needs no bespoke bindings — only the ambient authority the host forgot to withhold. `sandbox_boundary.rs` asserts each attempt is refused, the socket case against a live listener's own connection count. This matters because `wasmtime_wasi::p2::add_to_linker_sync` wires `wasi:filesystem`, `wasi:sockets/tcp` and `wasi:sockets/udp` into every guest's linker: what stops them is `SocketAddrCheck::default()` returning false and there being no preopens — **defaults in a crate we upgrade**. If either flips, the `host-fs` jail and the egress policy become decoration, and nothing else in the suite would notice.
- **Correct**: the stdin test's first version asked the probe to read and accepted "0 bytes" as success — which is what a test harness with no stdin returns whether or not the guest was granted any. It passed against the live hole. Piping a secret in by hand is what exposed it, so the test now re-executes itself with that secret on a pipe: a vacuum cannot be mistaken for a boundary when the pipe demonstrably has bytes in it. Verified by restoring `inherit_stdio` — the guest reads the secret and the test fails.
- The release bundle excludes the probe. It is inert unless enabled, but a release shipping a component called "escape probe" invites exactly one question.

## 2026-08-11

- **Fix (security)**: **Egress had no host-side boundary.** `host-http` handed every granted component an unrestricted client. The only destination check in the runtime lived *inside* `tool-fetch` — and a guard that runs in the sandbox is not a boundary. It protects a confused model from a URL the model chose; it says nothing about the component, which is the party this runtime declines to trust. A guest that simply omitted the check could reach `127.0.0.1:8787` (this gateway's own REST surface, unauthenticated by default on loopback), `169.254.169.254` (the cloud metadata service, which hands out IAM credentials to anything that asks), and everything else on the machine and the LAN. The policy is now host-side in `core::egress`: public destinations only, with loopback, private, link-local and unique-local refused. Hostnames are resolved before the decision, so a public name pointing at `127.0.0.1` is caught — which the guest-side guard explicitly could not do. Refusals reuse `connection-failed`, so the gate cannot be used as a port scanner.
- **Grant**: the allowance is **per-origin, not a switch**, because self-hosting means local models: `http://127.0.0.1:11434` is where Ollama lives, and a runtime that refuses it cannot talk to the private model it exists to serve. A boolean "allow local" would open every local port to solve that. Instead the operator has already written the origins down — a provider's `base-url`, an MCP server's `endpoint` — and those are lifted into the policy, with `network.allow` for anything else. Allowing the model's port does not allow the database beside it.
- **Fix**: `registry-mcp` received `host-http` unconditionally while a *tool* had to be granted `network: true` for the same capability — and it is the component whose whole job is talking to third-party servers. Its egress is bounded like everyone else's now.
- **Test**: the first version of `egress_boundary.rs` drove the staged `tool-fetch` at a live loopback server, and all three tests passed immediately. That was the tell: `tool-fetch` refuses loopback *itself*, so the sentinel saw nothing whether or not a host boundary existed — every assertion was vacuous. The tests now drive `fetch_within` (the function every guest-facing backend calls) against a real server and assert on the server's own request count, and a fifth reads the three host-side `host-http` implementations to insist none has gone back to the unbounded client. Verified by breaking each: removing the address check lets the sentinel be reached; pointing one backend at `http::fetch` fails the source check — *after* fixing that check, which matched only at line start and so passed against the backend I had deliberately broken. Same near-miss as the `export` extractor in the config test.

- **Test**: **`make gate` named the test files it ran, and the list was already stale.** `JK_REQUIRE_GUESTS` exists because a skipped test reports as passing — but the flag only applied to seventeen files someone had to remember to add, and `storage_scope` and `test_layout`, written and committed in the last two days, were not among them. The gate now runs `cargo test --workspace` under the flag: 40 test binaries instead of 17, and no list to forget. The forty-line comment explaining what each named file covered went with it.
- **Test**: **"Runs in any language" had no automated evidence.** Two documents called the TinyGo spike "the standing polyglot canary (`make gate`)"; `make gate` did not run it, and the Makefile says four lines away that the spike "stays opt-in: `make spike-guest`". The only thing exercising it was an example someone had to invoke by hand. `polyglot.rs` now loads the committed Go-built component, instantiates it in the real host with the real WASI wiring, and calls across the boundary — every gate run, no toolchain needed. A second test rebuilds it from source where `tinygo` and `wkg` are installed, which catches a `wit/` change a non-Rust toolchain cannot express; that one skips *audibly* rather than through `JK_REQUIRE_GUESTS`, because making an optional toolchain mandatory would only teach people to unset the flag. Both halves verified: the round-trip passes, and the rebuild fails as intended when the guest is broken.
- **Fix**: `tool_available` probed `--version` only, so it reported TinyGo — which answers `tinygo version`, and prints "Unknown command" with exit status 0 for the flag — as not installed. It tries both spellings now.

- **Fix (security)**: **The write tool was never gated.** The permission gate was a *denylist* of high-risk verbs — names containing `shell`/`write`/`exec`, `op` values like `write`/`delete`. `tool-edit` shipped with the ops `view`, `replace` and `insert`. None of those words is `write`, and `edit` is not `shell`, so the tool whose entire purpose is modifying files in place went through the gate **without ever asking**, from the commit that added it. Nothing failed, because a denylist that misses something is indistinguishable from one with nothing to catch. The gate is now an **allowlist** (`safe-calls`, default `[find, fs:read, fs:grep, git, edit:view, proc-probe]`): a call nobody has classified is confirmed, by construction. That is the only shape a fail-closed boundary can have — "these are dangerous" can only name the verbs someone thought of. The cost is real and worth stating: add a tool and it prompts until someone lists it. That is the correct direction for the mistake to point.
- **Fix**: the scope check scanned **every** string argument, so `tool-edit`'s `{"contents": "// edited"}` — a Rust, C, Go or JavaScript comment — was reported as "references a path outside the workspace". Scope escapes are deliberately un-rememberable, so the user could not silence it either. A gate that cries wolf about a code comment teaches people to click through it, which costs more than the narrow miss. It now inspects path-bearing keys (`path`, `file`, `dir`, `cwd`, `command`, …). Safe to narrow because it is not the enforcement: `host-fs` is path-jailed host-side and refuses an escape whatever the interceptor concluded.
- **Fix**: and the opposite miss, in the same check — `cat /etc/passwd` does not *start* with a slash, so testing the whole string caught nothing, and the call surfaced as the **rememberable** `shell:cat`, one "always" from standing approval to read any file on the machine. Path arguments are now checked per whitespace-separated token.
- **Test**: `an_edit_is_confirmed_before_it_touches_the_file` drives a real turn and asserts on the bytes on disk, refused *and* approved. The second half is what makes the first mean anything: `tool-edit` rejects an edit whose anchor no longer resolves, so a test with a made-up anchor would show "file unchanged" whether the gate existed or not — the first version of this test did exactly that, and passed for the wrong reason. The anchor is now read out of the `view` result the model was actually given.

## 2026-08-10

- **Retire**: **Storage is not an extension, and the `store-*` family never existed.** `config.yaml` had an `extensions.store` category; the architecture notes listed `store-sqlite`, `store-postgres` and `store-supabase` as components implementing `memory-store.wit`. Three of those names had no implementation. The fourth, `store-memory`, was resolved at boot, taken through `init` → `start`, and then never invoked — its `memory-store` exports had no caller anywhere in the host. The category's only real job was carrying `store.sqlite.path` for the core's own `rusqlite` database. So: `memory-store.wit` and `store-memory` deleted, `extensions.store` replaced by a top-level `storage: { path }`, and the docs corrected to describe what exists. The design intent was always host-side — the same page that listed the family said so — and it is the right call for a reason worth stating: the sandbox has no filesystem, so a store guest needs one granted back, and the transcript is the most sensitive thing here. "Swap your storage backend" means "hand your whole conversation history to a third-party component". Recorded in [decisions/2026-08-10](decisions/2026-08-10-storage-is-not-an-extension/Handoff.md).
- **Fix**: making a durable store the shipped default introduced a hazard the opt-in path never had: `./jan-klod.db` resolved against the **working directory**, and an installed jan-klod is launched from whatever repository the user is in — a stray database in each, and a different conversation history per directory. A relative `storage.path` now resolves against the directory holding `config.yaml`. Invisible in a checkout, where the two are the same place.

- **Grant**: **An interceptor can now keep state across restarts — only if it is granted that.** `host-storage` was a private `HashMap` per guest, so an interceptor that wanted to remember a context summary or a learned routing preference had nowhere to put it, while the core held an open `SQLite` connection for session transcripts three fields away. Wiring the two together is a one-line change that reads like an obvious fix. It is also how a security property dies: `interceptor-permission` keeps standing grants ("always allow `fs:write`") in `host-storage`, and documents them as **run-scoped, never persisted**, because "a permission boundary should not quietly become permanently open because of a click last week." Nothing enforced that — it held because the host had no other option. So durability is a per-instance grant (`persist: true`), default off, the same default-deny shape as `host-fs` and `host-process`; and one database behind every guest means isolation has to be enforced, so each instance's namespaces are prefixed with its own component id. A guest cannot name a peer's namespace or a session transcript, because it never gets to write the prefix.
- **Test**: `storage_scope.rs` asserts the property that was previously only described: a standing grant silences the gate within a run and is gone after a restart, an instance that opts in keeps its state, and neither can read the other's data. If the default ever flips, that first test fails.
- **Fix**: `list_namespaces` had never once succeeded. `SELECT DISTINCT … ORDER BY MIN(created_at)` is not valid `SQLite` ("misuse of aggregate"), and its only caller wrote `unwrap_or_default()` — so every session picker showed no sessions, and nothing said why. Grouped properly, covered by a test, and the caller now logs instead of swallowing.
- **Fix**: **Eighteen tests had not been compiled since the `src/` reorganisation.** `src/core/tests/` sits beside a *virtual* manifest (`[workspace]`, no `[package]`), so it belongs to no crate and cargo builds nothing in it. All eighteen pass now that they are in `core/tests/` — the loss was not a hidden failure but eighteen assertions defending nothing. This is the third variant of one failure mode: the hook that deleted `ext/`, tests that skipped themselves, and now tests that were never built. Each was invisible because the suite's own report is the thing under test, and it reads "passed" either way. `test_layout.rs` now fails if any `tests/` directory sits beside a manifest with no `[package]`.

- **Fix**: **The one route left unauthenticated was the one that approves a write.** The auth added in the previous commit runs in the router — but while a turn is parked on a confirmation, the waiting `PromptDriver` serves the socket *itself* and never passes through it. So with a token set, every endpoint was guarded except `POST /session/:id/answer`: an unauthenticated caller could answer "yes" to a permission prompt and cause a file write or a command to run. Shipped and fixed within the hour, by asking the question the last two path bugs should have trained: *which callers does this fix not reach?* The driver now checks the token itself, refusing with `401` and **continuing to wait**, so a refusal cannot consume the confirmation either. A wrong body looked exactly like a hang — worth noting because the next person to see a "hung" prompt test will reach for the concurrency first, as I did.

- **Implement**: **Bearer-token authentication on the REST surface.** The previous commit removed a config key that promised auth and delivered none; this builds the thing it promised, deliberately as its own change rather than a rider. - **Decide**: **Unset means open, `/health` is always open, and the secret lives in the environment.** Requiring a token to talk to your own loopback socket is friction without a threat, so the default is unchanged — and the exposure warning from the previous commit now *disappears once a token is set*, because a warning that survives doing what it asked is one people learn to skip. `/health` stays open because it carries no session data and the blue/green supervisor probes it without credentials during a flip. The token is an environment variable rather than a config key for the reason the old `api-key` was wrong twice over: a secret in a file people paste into issues. **No TLS**: stated in the quickstart, since a bearer token over plaintext protects only against callers who cannot read the wire.

- **Fix**: **`config.yaml` advertised an `api-key` for a surface with no authentication.** Applying the tell from the previous fix — *for each config block, name the code that reads it* — to every remaining block. `extensions.api.rest` named `bind:` and `api-key: ${REST_API_KEY}`; **nothing reads either**. `bind` comes from `serve --bind`, and `serve.rs` has no auth of any kind. That is not merely decoration like the others: a key called `api-key` invites someone to set it, bind to a routable address, and believe the surface is protected. It is not — anyone who can reach it can drive an agent that reads and writes a workspace. The block is replaced by a note saying so. `extensions.chat.telegram.token` was inert too (the token comes from `TELEGRAM_BOT_TOKEN`), and a secret in a config file is the wrong shape anyway; `store.postgres` is annotated like `tool.web-search`, a placeholder with no component.
- **Implement**: **The gateway warns when it is bound off loopback.** Documentation is not much protection at the moment someone types `--bind 0.0.0.0`, so `serve` now says, on stderr, that the surface is unauthenticated and what to do instead. A **warning, not a refusal**: binding elsewhere is legitimate behind a proxy that does authenticate, and a runtime refusing a documented address would be its own kind of lie — but it should not be quiet. Loopback in every spelling (`127.0.0.0/8`, `localhost`, `::1`) stays silent.

That fails as an unknown model, or resolves to something else entirely. Routing to a *provider* needs per-task reordering of a chain built at boot, and is not built.

The config block states plainly that it is inert until `interceptor.task-router` is enabled, and that enabling costs an extra model call per turn to classify the task — which is why it stays off by default rather than being switched on to make the block true.

- **Decide**: **The waiting turn serves the socket itself, rather than making the session `Send` and moving turns onto worker threads.** The loop is synchronous, so an `ask` *blocks inside* the open SSE response — and the answer has to arrive as a separate request while that response is still open, which a single-threaded server cannot accept. - **Implement**: **The prompt reaches the user and the answer gets back.** New `POST /session/:id/answer` route; a `prompt` SSE frame carrying question, options, and default; `StreamEvent::Prompt` and `answer_prompt` in the UI client. The REPL asks on the stdin it already owns; the TUI shows the question, retitles the input box with the options, and treats the next Enter as the answer to the waiting turn rather than a new message — an empty line takes the prompt's own default, so pressing Enter does the safe thing instead of sending `""`. ## 2026-08-08

- **Implement**: **Standing permission decisions — `always` / `never`.** `interceptor-permission` asked the same question on every dangerous call, which is the failure mode that gets a security boundary switched off entirely: a gate people disable protects nothing, so ergonomics here *is* a security property. The confirmation now accepts `always` and `never` alongside `yes`/`no`, recorded per **kind of action** and consulted before asking again. The scope key is the discriminator that matters — `op` for a multi-op tool (`fs:write`), the *program* for a command runner (`shell:cargo`, from `cargo test --workspace`), the bare name otherwise — so approving writes never approves deletes, and approving `cargo` never approves `curl`. Keying on the whole argument set would never match twice; keying on the tool alone would be a blanket grant.
- **Decide**: **Standing decisions are run-scoped, never persisted, and never cover a scope escape.** Three constraints keep the convenience from eroding the boundary. (1) They live in `host-storage`, which for an interceptor is memory owned by that instance — restart the agent and it asks again, because a permission boundary must not quietly become permanently open on the strength of one click last week. (2) `Concern::EscapesScope` is **un-rememberable**: "always allow writes" is about writing files, not about writing `/etc/passwd`. This is why `Policy::review` runs the **scope check first** — if a path escape were reported second, `{"op":"write","path":"/etc/passwd"}` would surface as the rememberable `DangerousOp` and a prior "always allow `fs:write`" would wave it through. (3) Every unreadable state — a storage error, a missing entry, a stored value that is not exactly `allow`/`deny` — falls back to asking; nothing can turn a broken read into an approval, and a failed *write* still lets the current call proceed (the user is simply asked again next time) so failing to persist a convenience never fails the security decision.
- **Implement**: **`tool-git` — read-only repository inspection.** New Rust guest in [src/extensions/tool-git/](../src/extensions/tool-git/), the 16th first-party component. The fleet could read, find, grep, and edit files but was blind to version control: checking its own diff meant enabling `tool-shell`, i.e. paying arbitrary command execution for `git status`. One tool, `git`, with five ops — `status`, `diff` (`staged`?, `path`?), `log` (`count`?, `path`?), `show` (`rev`), `branch`. The guest builds the argv itself from a closed op set, so the only program it can run is `git` and the only subcommands are those five. **There is no `commit`/`checkout`/`reset`/`push` — not disabled by policy, simply not expressible in the contract**, which is the difference between a capability granted and a capability *shaped*. Caller-supplied `rev`/`path` are validated (no leading `-`, restricted charset, length cap) and a pathspec is passed after `--`, because those two values are the only argv entries the model controls and `--upload-pack=…`-style options are how a value becomes a command.
- **Decide**: **Reading a repository is not inherently side-effect-free, so every invocation is hardened.** A checkout is data the agent did not write, and git treats parts of it as *configuration*: `.git/config` can point `core.fsmonitor` at a command that runs during `git status`, `core.hooksPath` at a directory of scripts, and `.gitattributes` can name external diff/textconv drivers that run during `git diff`. "Show me the diff" on a hostile repo is therefore a code-execution path. Every call carries `--no-pager --no-optional-locks -c core.fsmonitor=false -c core.hooksPath=/dev/null -c protocol.ext.allow=never`, and the diff-shaped ops add `--no-ext-diff --no-textconv`. Aliases need no guard — git refuses to let an alias shadow a real subcommand, and only real subcommands are emitted. This is the fail-closed boundary applied one level in: the sandbox already stops the *guest* from doing anything unexpected; this stops the *repository* from doing so.
- **Fix**: **`workspace:` and `execution:` were undocumented keys the core actually reads.** `Runtime::open_workspace`/`open_process_runner` read top-level `workspace:` and `execution:` (`enabled`/`timeout-secs`/`output-cap`) from config, but neither appeared anywhere in the shipped [config.yaml](../config.yaml) — so a user who enabled `tool.shell` (as its own comment invited) got a tool that failed closed with nothing explaining why, and the deployment-wide execution switch was invisible. Both are now written out with their defaults and their default-deny semantics stated. Same class as the earlier "shipped config gave a fresh install no tools" fix: the core's real contract has to be legible in the file users edit.
- **Implement**: **`tool-fs` `grep` searches a directory tree, not just one file.** Previously `grep` took a single `path` and returned `lineno:line` — so "where is this symbol?" cost the model a `find` plus a `read` per candidate, which is the sort of turn budget a small model does not have. `grep` now defaults `path` to the workspace root and searches the whole tree when `path` names a directory (probed by whether `list-dir` succeeds — `host-fs` has no `is-dir`, and widening the contract for a two-branch dispatch is not worth it), with an optional `glob` to narrow which files are read. Tree hits are prefixed `path:lineno:line`; a single-file `grep` keeps its old `lineno:line` shape. Bounded like the walk it rides on: 400 matches, then `…[partial: stopped at the match cap]`, and a walk bound is reported separately from a match bound so the caller can tell "too many hits" from "did not finish looking". A file that cannot be read (binary, not UTF-8, gone mid-walk) is skipped — one bad file must not cost the caller the other 200 results.
- **Refactor**: **Shared `guest-fs` library for the `host-fs`-routed guests.** `truncate` was duplicated byte-for-byte in `tool-fs` and `tool-edit`, and tree-grep would have made `tool-find`'s glob matcher and bounded walk a third copy. All of it — the output cap, the glob matcher, the bounded walk, and the cost bounds (`MAX_VISITS`/`MAX_DEPTH`/`MAX_RESULTS`/`MAX_OUTPUT_BYTES`, `PRUNED_DIRS`) — now lives in [src/extensions/guest-fs/](../src/extensions/guest-fs/), a workspace member that is **a library, not a component**: it holds no WIT bindings and imports no capability, so guests stay separate sandboxed components that merely compile the same tested logic in. Cost policy now has one place to change rather than three that can drift. [src/extensions/Makefile](../src/extensions/Makefile) gained a `LIBS` list so such crates are tested but never built to wasm or staged in `ext/`.
- **Fix**: **The roadmap claimed `tool-web-search` was built; it does not exist.** No `web-search` guest is in the tree (`config.yaml` carries only a disabled config placeholder) — the Phase 8 fleet table's *(built)* marker was wrong. Corrected, and `bash/shell` marked *(built)*, which it actually is.
- **Implement**: **`tool-find` — glob discovery over the workspace tree.** New Rust guest in [src/extensions/tool-find/](../src/extensions/tool-find/), the 15th first-party component, closing the fleet's discovery gap: `tool-fs` could `read`/`grep` a path it was *given* and `tool-edit` could patch one, but nothing could **enumerate** paths — a fresh session had no way to learn what files exist short of guessing them. One tool, `find`, taking `pattern` (+ optional `path` root): `*`/`?` match within a segment, `**` spans directories, and a pattern with no `/` is expanded to `**/<pattern>` so `Cargo.toml` finds the file wherever it lives (strict glob semantics would mean "repo root only", which is never what the caller meant). The walk is **guest-side over `host-fs`'s `list-dir`** — it sees exactly what the jail exposes, so no host-side directory-walking capability had to be granted.
- **Decide**: **A glob's cost is set by the tree, not the argument — so every dimension of the walk is bounded and a bound that bites is *said*.** `**/*` in a monorepo is one token from the model and unbounded work for the runtime, the one file operation where that asymmetry exists. Four caps: 20 000 entries visited, depth 24, 500 results, 64 KiB output. Heavy build/vendor trees (`.git`, `node_modules`, `target`, `.venv`, `__pycache__`, `.jj`) are pruned unless the pattern names one literally (`target/**/*.rs` opts back in). When a cap stops the walk the result appends `…[partial: stopped at the <bound>]`, and a byte-capped list appends the count omitted — a truncated tree must never read as an exhaustive one. An unreadable subdirectory is skipped, not fatal; only a root the jail refuses is an error.
- **Fix**: **The default boot plan (`jan-klod <config> <ext>` / `make run`) could not start any tool, registry, or interceptor.** `Runtime::start_all` instantiated *every* compiled component through the neutral `extension-world` linker, which grants only `host-log`/`host-config`/`host-http` — so a `tool-*` guest (imports `host-fs`/`host-process`), `registry-*` (`host-fs`/`host-event`), or `interceptor-*` (`llm-provider`) failed at instantiation. - **Implement**: **`tool-edit` — hash-anchored partial file edits.** New Rust guest in [src/extensions/tool-edit/](../src/extensions/tool-edit/), the 14th first-party component and the edit-reliability lever [small-model-harness.md](concepts/small-model-harness.md#edit-reliability-tool-edit--built) had specified but nothing implemented: until now the only way to change a file was `tool-fs`'s whole-file `write`, which is exactly the re-emit-the-whole-file failure mode small models fall into. One tool, `edit`, with three ops — `view` renders each line as `anchor|lineno|text`; `replace` swaps an anchor span (`end` defaults to `start`; empty `contents` deletes); `insert` places text `before`/`after` an anchor. `contents` must be *present* on `replace`/`insert` even when empty, so an omitted key cannot silently delete a span. An **anchor** is `fnv1a32(lineno \0 text)` in 8 hex, so it validates a line's position *and* content together: if the file changed since the model viewed it, no anchor resolves and the edit is **rejected with nothing written**. A hash collision resolves as ambiguous and is rejected the same way — a collision costs a retry, never a bad write. All I/O goes through the path-jailed `host-fs`, so the guest never touches the raw filesystem.
- **Decide**: **Recoverable edit rejections return `ok`, not `tool-error`.** `tool-callable`'s `tool-error` enum carries no message, and `tool_host` surfaces it to the model as the bare `tool \`edit\` error: ExecutionFailed` — from which a model cannot self-correct. Stale/ambiguous anchors therefore come back as an `ok` result reading `REJECTED (nothing was written): … Run op=view again and retry with fresh anchors.` `err` stays reserved for malformed arguments and `host-fs` failures. Fail-closed is about the *write*, which does not happen either way; the error channel is chosen for recoverability. This kept `wit/tool-callable.wit` unchanged.
- **Fix**: **The shipped `config.yaml` gave a fresh install no tools at all.** [docs/quickstart.md](quickstart.md) claimed "by default, only file access is enabled", but `extensions.tool` held only a disabled `web-search` placeholder — Phase 8's `tool-fs`/`tool-shell` were never added — and `interceptor.tool-selector` was disabled, so even an enabled tool is never advertised to the model at `select-tools`. Added `tool.fs` (enabled), `tool.edit` (enabled), `tool.shell` (disabled), and enabled `interceptor.tool-selector` + `interceptor.permission`. Net default posture: the agent can read and edit its workspace, every write is confirmed first, and shell execution stays opt-in — v0.1.0 completion criteria 2 and 3, which the shipped config did not actually meet.
